Andipatti Animal Feed System
Document 17 — Complete Backup, Disaster Recovery & Archival Architecture / Specification v1.0
Implementation-ready specification for protecting PostgreSQL transactional data, encrypted offline data, object/archive data, configuration, audit evidence and deployment state; recovering the platform after failure; and managing long-term archival without compromising financial, inventory, tax, audit or tenant integrity. No sprint planning.
1. Purpose, Scope, Objectives & Non-Goals
1.1 Purpose
Define the backup, restore, disaster recovery, business continuity, retention and archival architecture for the complete Andipatti Animal Feed System.
1.2 Scope
PostgreSQL authoritative transactional database.
Cloudflare R2 objects, attachments, exports and archive packages.
Redis/queue state where deployed and required for recovery.
Docker images, deployment configuration and infrastructure definitions.
Secrets/configuration recovery procedures without exposing secret values.
Flutter offline SQLCipher databases and device recovery.
Audit logs, financial evidence, compliance exports and archive manifests.
Backup verification, restore testing, disaster scenarios and operational runbooks.
1.3 Objectives
Minimize data loss and service downtime.
Recover to a known, internally consistent state.
Ensure backups cannot silently cross tenant boundaries.
Protect backups against unauthorized access, deletion and corruption.
Verify backups through automated integrity and restore tests.
Retain required financial/compliance evidence for the applicable policy.
Keep archival separate from primary backup so archival failure cannot eliminate recoverability.
1.4 Non-Goals
This document does not define legal retention periods; those must be approved against current requirements.
This document does not replace provider-specific disaster-recovery commitments.
No sprint planning is included.
2. Recovery Principles
PostgreSQL is the authoritative transactional source.
A backup is not considered valid until it is verified.
R2 archive storage is not the sole backup of PostgreSQL.
Backups must be encrypted and access-controlled.
Restore must preserve tenant isolation, accounting, inventory and audit integrity.
Point-in-time recovery is preferred where supported.
Recovery procedures are documented, automated where practical and regularly tested.
Archive packages are immutable/versioned where policy requires.
Never delete old primary records merely because an archive was created.
Recovery must account for external side effects such as payments, webhooks and compliance submissions.

4. RPO & RTO Framework
Final targets must be approved as business SLOs. The architecture supports the following target classes.

5. Backup Inventory
6. PostgreSQL Backup Strategy
Use provider-native automated backups where available.
Maintain independent logical/custom backups for portability where justified.
Enable WAL/PITR when supported and appropriate for required RPO.
Store backup copies outside the primary failure domain where feasible.
Encrypt backup artifacts.
Restrict backup access using least privilege.
Record backup metadata, timestamp, source environment and checksum.
Monitor backup success/failure.
7. Backup Types
8. Backup Frequency
Choose frequency from approved RPO rather than convenience.
At minimum, daily verified database backup is expected for a production baseline, subject to provider capabilities and approved policy.
WAL/PITR should be enabled when the required RPO cannot be met by daily backups.
Configuration and infrastructure state should be backed up/versioned continuously through protected source control and artifact storage.
Critical object data requires a documented backup/versioning policy.
9. Backup Encryption
Encrypt backups in transit and at rest.
Use managed KMS/encryption where available.
Separate backup access from normal application credentials.
Rotate encryption keys according to approved policy.
Document key recovery dependencies.
Do not store encryption keys beside unencrypted backup artifacts.
10. Backup Access Control
Application runtime must not have broad backup-administration privileges.
Only authorized operations roles can initiate restore.
Restore to isolated infrastructure by default.
Production overwrite restore requires explicit controlled authorization.
All backup/restore actions are audited.
Downloadable backup artifacts require strong authorization.
11. Backup Integrity Verification
Verify backup job completion.
Verify expected object/file size and metadata.
Verify checksum where applicable.
Verify encryption metadata.
Periodically restore into an isolated environment.
Run database integrity/reconciliation checks.
Run application smoke tests.
Record restore duration and outcome.

13. Restore Validation — Mandatory Checks
14. Point-in-Time Recovery
Identify target recovery timestamp.
Freeze affected application writes if required.
Restore base/full backup.
Replay WAL/logs to target.
Validate database consistency.
Reconcile transactions around the recovery boundary.
Start application in controlled mode.
Run smoke and financial/inventory reconciliation.
Resume normal traffic only after approval.
Recovery to a time before a known bad transaction requires explicit analysis of external side effects; restoring the database alone cannot automatically reverse an external payment or government-provider action.

18. PostgreSQL Recovery Architecture
Use separate roles for application, migration, reporting and backup operations.
Restore roles/permissions as part of infrastructure recovery.
Reapply RLS policies and security configuration.
Verify extensions and version compatibility.
Validate sequences/document-series behavior after restore.
Verify financial-year state.
Check indexes and constraints.
Run reconciliation before accepting new financial transactions.
19. Sequence & Document Number Recovery
Invoice/document series must remain unique after restore.
Never manually guess the next invoice number.
Verify sequence state against authoritative document records.
If a recovery creates uncertainty around numbering, freeze finalization until reconciled.
Financial-year boundaries must be revalidated after recovery.
20. Payment Recovery
Identify provider transactions around the recovery window.
Replay provider webhooks through idempotent processing where safe.
Reconcile provider statements against internal payment records.
Do not manually mark payments Paid without authoritative evidence.
Investigate duplicate/unknown outcomes.
Record all recovery decisions in audit records.
21. GST/Compliance Recovery
Preserve invoice tax snapshots.
Preserve compliance request/response evidence.
Identify submissions made externally before recovery.
Reconcile e-invoice/e-way state with providers.
Do not blindly resubmit without idempotency/reference checks.
Regenerate exports from authoritative restored data and compare.
22. Inventory Recovery
Restore stock movements and balances.
Reconcile balances from movement ledger.
Verify reservations are not stale.
Verify batch/expiry status.
Verify FIFO/FEFO allocation history.
Investigate sales/returns around recovery point.
Perform controlled physical count when data integrity is uncertain.
23. Accounting/Khata Recovery
Verify every journal balances.
Reconcile customer ledger to invoices/receipts.
Reconcile supplier payables to GRNs/payments.
Verify refund/credit-note lineage.
Reconcile EOD sessions.
Freeze financial posting if reconciliation fails.
24. Offline Device Recovery
Server data remains authoritative.
Lost/stolen device is revoked.
SQLCipher local DB is encrypted and key-protected.
Pending local transactions are reconciled after device recovery.
Duplicate/replayed envelopes are rejected idempotently.
If local data is irrecoverable, rebuild from server master data and supported history.
Do not copy raw SQLCipher keys into support channels.
25. R2/Object Recovery
Use private buckets/objects.
Use versioning/retention controls where supported.
Store archive objects with checksums.
Keep archive manifests in authoritative DB and protected backup.
Use server-generated object keys.
Use short-lived signed URLs for recovery/download.
Verify object integrity after restore.
26. Archive vs Backup
The system must maintain both concepts independently.
27. Archival Eligibility
Eligibility is policy-driven, not simply 'older than 365 days and paid'.
Consider financial period closure, legal retention, audit holds, disputes, refunds, pending compliance, unresolved reconciliation and operational dependencies.
Only immutable/closed records should be candidates for archival.
Archive manifests identify exactly which records and objects are included.
28. Archive Package Design
29. Archive Integrity
Serialize records deterministically.
Generate cryptographic checksums.
Store manifest with record counts.
Upload encrypted archive object.
Verify uploaded object.
Record archive object/version.
Run restore/read verification.
Mark archive complete only after verification.
30. Archive Lifecycle
31. Archive Deletion / Destruction
Never destroy solely because a record is old or paid.
Check retention policy and legal/audit holds.
Require authorized deletion policy.
Destroy both metadata/object copies where required.
Record destruction event and scope.
Retain evidence of destruction where policy requires.
Ensure backups containing the data follow their own retention lifecycle.
32. Archive Restore

Identify tenant and period.
Retrieve manifest.
Verify object checksum.
Decrypt using controlled key access.
Validate schema/version compatibility.
Load into isolated read-only environment.
Run record-count and financial/inventory reconciliation.
Expose to authorized user only.
Record restore audit event.
33. Retention Policy Model
Actual durations must be configured from approved legal/business policy and reviewed periodically.
34. Legal/Audit Hold
Hold can prevent archival destruction.
Hold applies to identified tenant/records/periods/objects.
Hold creation/release is authorized and audited.
Archive jobs skip held data from destruction.
Reports expose held status to authorized administrators.
35. Backup Retention
Use layered retention: recent frequent backups, periodic longer-lived backups and disaster-recovery copies.
Align retention to approved RPO/RTO and compliance requirements.
Avoid uncontrolled accumulation of backups.
Test that retention automation does not delete the only recoverable copy.
36. Backup Immutability
Use immutable/WORM-style controls where available for critical recovery copies.
Separate backup administration from application administration.
Prevent ordinary application credentials from deleting backups.
Monitor unexpected backup deletion/retention-policy changes.
Test ransomware-like recovery using isolated copies.
37. Disaster Recovery Environments
38. DR Network Security
Recovery environments use the same or stronger network segmentation.
Database ports are private.
Administrative access uses controlled identities.
TLS remains mandatory.
Recovery credentials are not shared in chat or documents.
R2/object access is least-privileged.
39. Secret & Key Recovery
Document where production secrets are managed without recording secret values.
Maintain emergency access procedures.
Test key recovery before a disaster.
Rotate compromised secrets immediately.
Verify payment/GST/WhatsApp credentials after recovery.
Keep separate credentials for backup and application operations.

50. File & Export Recovery
Identify whether an export is reproducible from authoritative data.
If reproducible, prefer regeneration rather than treating temporary export files as primary data.
Long-lived compliance evidence is archived according to policy.
Verify checksums for retained files.
Protect exported PII and tax data.
51. Log & Audit Recovery
Security and audit records needed for incident investigation must have protected retention.
Application logs are not a substitute for authoritative audit tables.
Logs may be reconstructed only as observability evidence, not as financial truth.
Redaction policies remain active during recovery.
52. Redis / Queue Recovery
Redis is not authoritative for financial/inventory state.
Rebuild caches from PostgreSQL where possible.
Use durable outbox/integration event records for important asynchronous work.
After queue loss, identify pending events from authoritative outbox state.
Avoid blindly replaying non-idempotent external side effects.
53. Scheduled Job Recovery
Jobs have unique IDs and idempotency where appropriate.
After restore, determine jobs that were running at the recovery point.
Prevent duplicate execution of financial/compliance side effects.
Resume safe read/report jobs first.
Reconcile payment/compliance jobs before replay.
54. Device Theft/Loss
Mark device revoked.
Invalidate device sessions/tokens.
Stop synchronization.
Assess pending offline transactions.
Issue replacement device credentials.
Verify no secrets are exposed.
Audit the incident.
55. Ransomware / Malicious Deletion Recovery
Isolate affected infrastructure.
Do not trust compromised application credentials.
Preserve forensic evidence.
Revoke/rotate credentials.
Use clean immutable backups.
Rebuild infrastructure from trusted images/source.
Restore database and objects.
Run full security/reconciliation tests.
Resume only after containment and validation.
56. Business Continuity During DB Outage
Offline POS can continue only within the documented offline policy.
Do not expand offline permissions merely because the server is down.
Payment state remains subject to authoritative confirmation.
Operators should see clear outage/offline status.
When restored, synchronize and reconcile before normal confidence is assumed.

70. Non-Negotiable Backup/DR Rules
R2 archives are not the sole PostgreSQL backup.
Never declare a backup recoverable without restore verification.
Never delete old transactions solely because they are archived.
Never overwrite historical archive packages without versioned control.
Never restore directly over production without controlled authorization.
Never trust application credentials as backup-admin credentials.
Never resume financial posting when reconciliation is unresolved.
Never blindly replay payment or compliance side effects after recovery.
Never expose backup/archive files through public URLs.
Never allow recovery procedures to bypass RLS, authorization or audit controls.

72. Final Backup, DR & Archival Architecture Summary
The system uses layered resilience: authoritative PostgreSQL backups and point-in-time recovery protect transactional state; protected object storage protects files and archives; immutable/versioned copies protect against destructive incidents; Docker/IaC artifacts allow clean infrastructure reconstruction; offline SQLCipher data is treated as recoverable operational state rather than the source of truth; and every recovery ends with tenant, financial, inventory, payment and compliance reconciliation. Archival is a separate long-term retention function and never substitutes for backup.
