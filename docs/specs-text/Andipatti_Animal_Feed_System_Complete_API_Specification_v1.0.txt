ANDIPATTI ANIMAL FEED SYSTEM
COMPLETE API SPECIFICATION
Version 1.0 • Go REST API + WebSocket + Offline Sync + Webhooks
This document is the implementation-level API contract following the Complete Database & ERD Specification v1.0 and Final Master PRD v1.2. It defines authentication, authorization, tenant isolation, request/response conventions, endpoints, validation, idempotency, synchronization, payments, hardware events, notifications, compliance, reporting and operational APIs.
Tax/HSN, e-way-bill, payment-provider and WhatsApp behavior must remain configuration/provider driven and must be validated against current applicable rules before production.
1. API Architecture
Base URL: /api/v1.
Transport: HTTPS/TLS for REST; WSS for WebSocket.
Content type: application/json unless an endpoint explicitly accepts multipart/form-data or file download.
PostgreSQL is authoritative; API is the only normal write boundary.
Go services must enforce tenant authorization before database access and establish trusted PostgreSQL tenant context for RLS.
External APIs are isolated behind provider adapters.
Large reports/exports are asynchronous jobs.
Financial writes use DB transactions and outbox events.
2. Standard Headers
The server generates a correlation ID if X-Request-ID is absent. Never trust tenant_id supplied in a request body as authorization context.
3. Authentication
3.1 Login request/response
POST /api/v1/auth/login
Request: {identifier, password, device_id, device_fingerprint}
Response: {access_token, refresh_token, expires_in, user, tenant, permissions, device}
Security: rate limiting, lockout policy, generic failure messages, audit logging.
3.2 Token rules
Short-lived access tokens.
Refresh tokens rotated and revocable.
Device/session can be independently revoked.
Do not store access tokens in plaintext local DB.
4. Authorization & RBAC
Every protected endpoint maps to one or more permission codes. Example: invoice.create, invoice.finalize, invoice.cancel, stock.adjust, credit.override, payment.refund, eod.close, archive.purge.
403 when authenticated but not authorized.
401 when authentication is absent/invalid.
Authorization checks are server-side; UI hiding is not security.
Tenant is derived from trusted identity/session and device registration.

6. Pagination, Filtering & Sorting
Collection endpoints use limit, cursor, sort and filter parameters. Cursor pagination is preferred for high-volume data.
Response pattern: {data:[...], page:{next_cursor, has_more}, request_id}. Never expose unbounded collections.
Default limit 25/50 according to endpoint.
Maximum limit configured globally.
Date filters use ISO/RFC3339 or YYYY-MM-DD where the endpoint is date-based.
All queries are tenant scoped.

8. Users, Roles & Devices
9. Product APIs
Search supports q, barcode, sku, language, alias, active and cursor. Exact barcode/SKU has highest priority. Fuzzy/phonetic matching is bounded and indexed.
10. UOM APIs
Conversion results use decimal-safe values. The API must return factor, source UOM, target UOM and effective rule used.
11. Tax & Pricing APIs
Tax profiles must be validated/approved according to tenant policy. Historical invoices store snapshots.
12. Customer APIs
Credit check response includes current outstanding, available limit, proposed credit, post-transaction balance, whether approval is required and applicable policy.
13. Supplier APIs
14. Procurement / PO APIs
PO lines include product, UOM, quantity, unit cost, discount, tax profile and expected delivery. Approval is permission-controlled.
15. GRN APIs
Validation must calculate gross/tare/net, verify tare threshold, batch/expiry, UOM, cost, supplier and quality status. Over-threshold tare requires correction or authorized override.
16. Inventory APIs
Stock queries support location, product, batch, status and UOM. Posted movement records are immutable; corrections are reversal/adjustment operations.
17. POS Cart & Quote APIs
Cart is a convenience object; the finalized invoice is authoritative. A quote must never reserve stock unless explicitly configured.
18. Invoice APIs
Finalization is atomic and idempotent. An invoice response includes invoice ID, invoice number, totals, taxes, payment status, batch allocations and print/delivery status references.
19. Invoice Finalization Request
POST /pos/carts/{id}/finalize
{
  "customer_id": "uuid|null",
  "tenders": [
    {"method":"CASH","amount":"1000.00"},
    {"method":"UPI","amount":"500.00","payment_intent_id":"uuid"},
    {"method":"CREDIT","amount":"1500.00"}
  ],
  "notes": "optional"

Rules:
- tender sum equals grand total;
- credit is validated against limit;
- stock allocation is validated;
- tax snapshot is generated;
- idempotency key is mandatory;
- all financial/stock records commit atomically.
Use strings for decimal JSON values where client/platform precision could otherwise be unsafe.
20. Returns & Refund APIs
21. Khata / Receipts / Contra APIs
Receipt and contra posting are atomic with ledger/journal effects. Contra valuation must use approved pricing/authorization.
22. Payment APIs
Webhook endpoint must verify provider signature, event ID uniqueness and payload integrity before financial processing. Provider credentials are never accepted from clients.
23. Payment Webhook Processing
Receive request and capture provider event ID.
Verify signature/authentication.
Check provider + event ID uniqueness.
Validate amount/currency/reference.
Locate internal payment intent.
Lock/validate relevant transaction state.
Apply state transition idempotently.
Create ledger/journal effects only once.
Create outbox event.
Return provider-required success response.
Retry transient internal failures safely.
24. Device / Hardware APIs
Actual Bluetooth/USB/serial communication normally occurs on-device. The API stores device configuration, diagnostics and audit events rather than attempting to directly control local hardware.
25. Receipt Delivery / WhatsApp APIs
WhatsApp receipt delivery is asynchronous. A printer failure can trigger a UI fallback action, but the delivery itself does not alter invoice financial state.
26. Khata Collection Grace Period APIs
The collection engine must deduplicate by tenant + customer + cycle + template version. Grace periods suppress messages without changing receivable due dates.
27. EOD APIs
EOD close records opening cash, cash sales, refunds, payouts, expected cash, actual cash and variance. Reopen requires privileged approval and audit.
28. Compliance APIs
Eligibility and required fields are determined by current applicable rules/configuration. Provider responses must be stored with request/response references and status.
29. Reports APIs
All report filters are tenant-scoped and RBAC-controlled. Large exports return a job ID.
30. Offline Sync APIs
30.1 Push envelope
{
  "device_id":"uuid",
  "transactions":[{
    "client_transaction_id":"uuid",
    "local_sequence":1234,
    "entity_type":"SALES_INVOICE",
    "operation_type":"CREATE",
    "payload_version":1,
    "payload_hash":"sha256...",

Server validates device ownership and tenant context.
Each transaction is independently idempotent.
Response contains ACCEPTED, DUPLICATE, CONFLICT or REJECTED per transaction.
Batch upload is not one giant transaction if doing so would make retry/diagnostics unsafe; each financial transaction remains atomic.
31. Sync Conflict Semantics
Last-write-wins is prohibited for financial and inventory events.
32. WebSocket API
WSS /api/v1/ws
WebSocket is supplementary; REST/database remains authoritative.
Clients reconnect with backoff.
Events include event_id, type, aggregate_id, tenant context implicitly, sequence/timestamp and payload version.
Duplicate events are safe to process.
33. Outbox / Event Delivery
Within the same DB transaction as the business event, insert an integration_events/outbox row. A worker publishes it after commit. External delivery is retryable with exponential backoff and dead-letter handling.
No external API call inside a long-held DB transaction.
Events have unique IDs.
Consumers must be idempotent.
Failed events remain observable and replayable by authorized operators.
34. API Validation Rules
UUID syntax validated.
Tenant identity never accepted as a trust boundary from client input.
Decimal strings validated for scale and range.
Dates/timestamps validated and normalized.
Enum/status values validated.
Referenced records must belong to the same tenant.
Inactive/deactivated products cannot be newly sold.
Expired/quarantined batches cannot be allocated to ordinary sales.
Invoice tender total must equal invoice grand total.
Credit tender must pass credit check.
GRN net weight cannot be negative.
Tare threshold must be enforced.
Finalized documents cannot be mutated through generic PATCH.
35. Idempotency Contract
Required on: invoice finalization, payment intent creation, receipt posting, contra posting, return posting, refunds, stock adjustments, EOD close, compliance submissions and sync push.
Header: Idempotency-Key.
Server stores operation result with tenant + operation + key.
Same key + same payload returns original result.
Same key + materially different payload returns 409 IDEMPOTENCY_CONFLICT.
Retention must cover realistic client retry windows and offline synchronization windows.
36. Rate Limits
Exact values are load-tested and configurable; do not hard-code production assumptions.
37. API Security
TLS only in production.
JWT/session validation.
RBAC + RLS.
Rate limiting.
Input validation.
Request size limits.
Audit privileged writes.
Secrets never in responses.
Provider webhook verification.
Sensitive endpoints require recent authentication/step-up approval where configured.
Do not log passwords, tokens, payment credentials or sensitive personal payloads.
38. API Versioning
URI version /api/v1.
Breaking changes require new major API version.
Additive response fields should be backward compatible.
Clients advertise app version.
Server maintains a compatibility matrix for supported Flutter versions.
Deprecated endpoints return documented deprecation metadata before removal.
39. File APIs
Object storage is preferred for large files. Uploads require MIME/size/checksum validation. Access is tenant/RBAC controlled.
40. Archive APIs
Purge is never automatic merely because data is older than 365 days and paid. It requires policy eligibility, successful archive verification and privileged authorization.
41. Health & Operations APIs
Health endpoints must not expose secrets or internal infrastructure details publicly.
42. API Audit Requirements
Every privileged write records actor, device, request ID, entity, before/after where appropriate and reason.
Authentication events are audited.
Payment webhooks record provider event ID and verification result.
Sync conflicts/resolutions are audited.
Archive/purge actions are audited.

47. Final API Design Principle
The API must make invalid financial and inventory states difficult or impossible to create. The client is a user interface and offline execution environment; the Go API is the authoritative business-rule boundary; PostgreSQL/RLS is the final data-isolation boundary. Every externally visible side effect is asynchronous/idempotent where possible, and every material business event is traceable through invoice, stock, payment, ledger, journal, sync and audit identifiers.
