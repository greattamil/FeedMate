Document 19 — Complete Implementation & Build Specification v1.0
Implementation-ready engineering specification translating Documents 01–18 into an executable build contract for Flutter, Go, PostgreSQL, Docker, integrations, hardware, testing, deployment and production operations. No sprint planning.
1. Purpose, Scope, Objectives & Non-Goals
1.1 Purpose
Provide the complete build-level contract: repository structure, coding standards, module boundaries, database migration order, API implementation, frontend implementation, offline synchronization, hardware adapters, financial/inventory transaction boundaries, Docker deployment, testing gates and production acceptance.
1.2 Scope
Flutter mobile client and local SQLCipher database.
Go backend modular monolith and workers.
PostgreSQL authoritative database with RLS.
Redis/queue where enabled.
Cloudflare R2 object/archive storage.
REST API and WebSocket events.
POS, inventory, procurement, accounting, Khata, payments, GST/compliance, reports and hardware.
CI/CD, Docker and infrastructure.
Observability, security, backup/DR and release controls.
1.3 Non-Goals
No sprint planning or sprint schedule.
No permanent hardcoding of legal tax rates or thresholds.
No replacement of official provider certification or legal review.
2. Implementation Principles
PostgreSQL is the authoritative transactional source.
Go is the business-rule and authorization boundary.
Flutter is offline-first but never authoritative for financial truth.
Every tenant-owned table is tenant-scoped and protected by RLS.
Financial and inventory writes are atomic.
External side effects are asynchronous, signed/idempotent and auditable.
Decimal types are mandatory for money, tax, quantity and conversion-sensitive values.
Finalized financial documents are immutable; corrections use returns, reversals or credit/debit notes.
All production services run in Docker-compatible environments.
Every implementation feature must map to a requirement, API, DB model, UI, test and operational control.

10. PostgreSQL Implementation Rules
Use NUMERIC(12,2) or stronger for currency.
Use NUMERIC(12,3) for weight/quantity baseline.
Use NUMERIC(12,6) for UOM factors.
Use NUMERIC(7,4) for tax rates.
Use UUID or equivalent stable IDs.
Use UTC timestamps with tenant-local presentation.
Use composite tenant-aware foreign keys where appropriate.
Use CHECK constraints for non-negative quantities and valid states.
Use unique constraints for tenant-scoped natural identifiers.
Enable RLS on every tenant-owned table.
11. Transaction Boundary Rules
External network calls must not be placed inside a long database transaction unless a provider-specific safe orchestration requires it. Use payment intent/outbox patterns.
12. Idempotency Implementation
Require Idempotency-Key for designated financial mutation endpoints.
Persist tenant + endpoint + key + request hash + outcome.
Reject same key with materially different payload.
Webhook event IDs are unique.
Outbox events have stable IDs.
Replay returns the original authoritative result.
Idempotency records have documented retention.
13. Concurrency Controls
Lock stock rows/batch allocation candidates during finalization.
Use deterministic lock ordering.
Prevent negative stock unless explicitly configured.
Use optimistic version fields where appropriate.
Use serializable/appropriate isolation only where justified.
Retry serialization/deadlock failures safely.
Never retry a non-idempotent external side effect blindly.

95. Final Architecture Summary
The implementation is a tenant-isolated, transactionally consistent, offline-first animal-feed retail platform. Flutter provides fast local operation and hardware integration; Go owns business rules and external orchestration; PostgreSQL owns authoritative financial/inventory state with RLS; Redis is optional and rebuildable; R2 stores protected objects/archives; Docker provides reproducible deployment; CI/CD enforces quality and security; and every production release is supported by backup, restore, reconciliation, monitoring and audited operational controls.
