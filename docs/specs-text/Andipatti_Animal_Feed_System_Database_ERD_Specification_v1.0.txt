ANDIPATTI ANIMAL FEED SYSTEM
COMPLETE DATABASE & ERD SPECIFICATION
Version 1.0 • Implementation Baseline • PostgreSQL + Flutter SQLCipher Offline Store
This document is the database-level companion to the Final Master PRD v1.2. It is intentionally exhaustive and defines the logical model, physical PostgreSQL model, tenant isolation, accounting/inventory ledgers, offline synchronization, integrations, auditability, indexing, constraints, partitioning, retention and migration rules.
Regulatory values such as tax rates, HSN classification, statutory thresholds and provider-specific fields are configuration-driven and must be validated against current applicable rules before production.
1. Database Design Objectives
PostgreSQL is the authoritative transactional source of truth.
Every tenant-owned row is tenant-scoped and protected by application authorization plus PostgreSQL Row-Level Security (RLS).
Financial and inventory events are append-oriented and auditable; derived balances are projections/caches.
Money uses NUMERIC(12,2) unless a wider approved precision is required.
Weight and inventory quantities use NUMERIC(12,3); UOM factors use NUMERIC(12,6).
All authoritative financial timestamps are server-generated and timezone-aware.
Offline transactions use UUIDs, device identity, local sequence and idempotency keys.
Historical transactions retain snapshots of the master data needed to reproduce the original result.
Referenced master records are deactivated rather than physically deleted.
Database migrations are version-controlled and tested.

25.4 Offline transaction rules
Write transaction locally in SQLCipher.
Assign UUID client_transaction_id and monotonic local_sequence.
Hash/integrity-protect the envelope.
Upload with idempotency key.
Server validates tenant/device/auth/business rules.
Server atomically posts the transaction or returns a deterministic conflict/error.
Client records authoritative IDs/result.
Retries return the original result for duplicates.
Rejected transactions remain visible with actionable resolution status.

31. PostgreSQL RLS Requirements
RLS is mandatory for tenant-owned tables.
Enable ROW LEVEL SECURITY and FORCE ROW LEVEL SECURITY where appropriate.
Application database role must not be a superuser and must not have BYPASSRLS.
At transaction start, Go establishes trusted tenant context after authentication/authorization.
Policies use current_setting('app.tenant_id', true) converted to UUID, with fail-closed behavior when absent/invalid.
INSERT/UPDATE policies require NEW.tenant_id to match the trusted context.
SELECT/DELETE policies require row tenant_id to match.
Cross-tenant administrative operations use a separately authorized service path with explicit controls.
CI tests must verify RLS on every tenant-owned table.
Illustrative policy pattern: CREATE POLICY tenant_isolation ON table USING (tenant_id = current_setting('app.tenant_id', true)::uuid) WITH CHECK (tenant_id = current_setting('app.tenant_id', true)::uuid); Production implementation must additionally handle missing context safely and test role permissions.
32. Indexing Strategy
Use PostgreSQL full-text/trigram indexes only where justified. For Tamil/local alias search, validate PostgreSQL collation/extension behavior; otherwise maintain normalized searchable columns or a dedicated search service.
33. Constraints & Integrity Rules
All monetary amounts >= 0 unless a signed adjustment field is explicitly defined.
Invoice grand_total = subtotal - discounts + tax + charges + rounding according to one deterministic formula.
Invoice tender total = grand_total.
Posted journal entry debits = credits.
Stock movement signed quantity is derived from movement type and cannot be arbitrary without a privileged adjustment type.
GRN net_weight = gross_weight - tare_weight and net_weight >= 0.
Tare_weight <= gross_weight × configured maximum percentage unless approved override.
Inventory quantity must not be negative unless an explicit tenant policy allows it; offline conflict rules must still prevent accidental negative stock.
Expired/quarantined batches cannot be allocated to normal sales.
Historical invoice snapshot fields cannot be updated after finalization.
Referenced master rows cannot be physically deleted.
All tenant FKs should include tenant consistency checks where feasible, or composite tenant-scoped FK patterns for critical tables.
34. Composite Tenant Foreign Keys
For high-integrity tables, prefer composite uniqueness and foreign keys such as UNIQUE(tenant_id,id) on parent tables and FOREIGN KEY(tenant_id,parent_id) REFERENCES parent(tenant_id,id). This prevents an accidental cross-tenant foreign-key reference even if application code is defective. This complements RLS.
35. Transaction & Locking Rules
Invoice finalization uses one DB transaction for invoice, lines, taxes, tender allocation, batch allocation, stock movements, customer ledger and journal entries.
Stock allocation locks the relevant balance/batch rows or uses serializable-safe logic.
Document number allocation uses SELECT FOR UPDATE or an equivalent atomic sequence strategy.
Payment webhook processing uses unique provider event IDs plus transaction locking/idempotency.
EOD close locks the applicable business date/session.
Do not hold DB transactions open while calling external APIs.
Use an outbox record within the transaction and publish externally after commit.
36. Partitioning Strategy
Consider range partitioning high-volume tables by financial year/month: sales_invoices, sales_invoice_lines, stock_movements, customer_ledger_entries, supplier_ledger_entries, audit_logs and integration_events.
Partitioning must preserve tenant isolation and index performance.
Archive operations can operate at partition granularity where policy permits.
Partition keys must be stable and must not prevent efficient tenant/date queries.
Do not introduce partitioning solely for theoretical scale; benchmark first.
37. Retention & Purge
Retention policy must be documented per data class.
Financial/statutory records cannot be purged solely because they are paid.
Archive eligibility must consider legal/accounting retention, open disputes, returns, audits, compliance, restoration requirements and business policy.
Purges are privileged, logged and preferably soft/partition-based.
Before purge: manifest → object upload → checksum verification → restore verification → approval → purge.
Keep archive_catalog/manifest metadata live so archived records remain discoverable.
38. SQLCipher Offline Database Scope
Local tables mirror only the minimum operational subset: products, aliases, prices, customers, credit profile snapshot, active batches/stock snapshot, invoice drafts, offline invoices, local payments, sync queue, device configuration and pending receipts.
Do not replicate unnecessary historical financial data to the device.
SQLCipher key is held through platform secure storage; never hard-code it.
Local data must include schema version and migration state.
Local purge follows device lifecycle policy after server acknowledgement where possible.
39. Recommended Local Tables
local_products, local_product_aliases, local_prices, local_customers, local_credit_snapshots, local_batches, local_stock_balances, local_invoices, local_invoice_lines, local_tenders, local_batch_allocations, local_sync_transactions, local_sync_conflicts, local_device_state, local_receipt_jobs.
Local schemas may differ physically from PostgreSQL but must preserve the fields required for deterministic synchronization and audit.
40. Data Types & Serialization Rules
Go must not use float32/float64 for money or precision-sensitive weight/quantity calculations.
API JSON should serialize decimal values in a deterministic representation; string-decimal transport is acceptable and often safest.
Flutter should use Decimal/fixed-precision representations rather than double for financial calculations.
All IDs are strings in JSON when UUIDs are used.
TIMESTAMPTZ is serialized as RFC 3339 with offset/UTC.
Nullability in OpenAPI must exactly match PostgreSQL/business semantics.
Scale/precision validation occurs at API boundary and DB constraint level where possible.
41. Soft Delete Rules
Products, customers, suppliers, price lists, aliases and devices may be deactivated.
Finalized invoices, posted payments, posted stock movements, journal entries and ledger entries are never physically deleted by ordinary application actions.
Corrections use reversal/adjustment records.
Archive/purge is a separate privileged process governed by retention policy.

Create tenants/configuration.
Create identity/RBAC.
Create product/UOM/tax/pricing.
Create customer/supplier.
Create locations/procurement.
Create inventory/batch.
Create sales/payment/ledger/journal.

Seed approved reference data.
Run migration tests against empty and representative datasets.
44. Database Migration Rules
Every migration has a unique ordered version.
Backward-compatible expand/contract approach for live deployments.
Avoid long blocking locks during business hours.
Large data backfills are asynchronous/batched.
No destructive migration without explicit backup and rollback plan.
Schema changes must update ERD and API contracts.
45. Backup & Restore
Automated encrypted backups.
Point-in-time recovery where available.
Separate backup credentials/storage.
Restore tests at scheduled intervals.
Validate row counts, checksums, key balances and sample invoice/ledger traces after restore.
R2 archive objects are not a replacement for primary DB backups.
46. Security
Least-privilege PostgreSQL roles.
No superuser from application.
No BYPASSRLS.
TLS in transit.
Encryption at rest where infrastructure supports it.
Secrets through secret manager/environment, never source.
Audit privileged operations.
Restrict raw JSONB payload access when it may contain personal or provider-sensitive data.
Rotate credentials and provider keys.

Stock: sum stock movements vs stock_balances.
Customer: sum customer ledger vs credit profile balance projection.
Supplier: sum supplier ledger vs payable projection.
Invoice: lines + taxes + tenders + ledger + stock allocations.
Journal: total debits vs credits.
Payment: provider events vs internal payments vs invoice allocations.
Archive: manifest counts/checksums vs source selection.

56. Final Design Principle
The database is not a collection of CRUD tables. It is the financial, inventory and audit backbone of the business. Product masters describe what can be sold; stock movements describe what physically happened; invoices describe what was sold; payments describe how it was settled; customer/supplier ledgers describe who owes whom; journals describe the accounting effect; sync records describe how offline actions reached the authority; audit records describe who changed what; archive manifests describe how historical evidence is preserved.
This model is the authoritative database baseline for the next documents: Complete API Specification, Go Backend Technical Architecture, Flutter Architecture, Offline Synchronization Specification, Inventory & Batch Engine Specification, Accounting & Khata Specification and POS/Billing Engine Specification.
