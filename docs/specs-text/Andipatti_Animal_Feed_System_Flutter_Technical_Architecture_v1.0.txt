Document 04 — Complete Flutter Technical Architecture Specification
v1.0 — Implementation Baseline
Aligned with PRD v1.2, Database & ERD v1.0, API Specification v1.0, and Go Backend Technical Architecture v1.0.
Client baseline: Flutter + Dart, offline-first, SQLCipher SQLite, secure device storage, REST/WebSocket synchronization, and direct hardware integration at the shop edge.
1. Purpose & Scope
This document defines the complete Flutter application architecture for Android/tablet/phone shop devices. The application is designed for unreliable connectivity, fast POS operation, Tamil/local-language usage, barcode and weighing hardware, thermal printing, payment status updates, and safe synchronization with the authoritative Go/PostgreSQL backend.
Flutter is the user interface and offline execution environment, not the authoritative financial database.
SQLCipher SQLite is the encrypted local operational store.
PostgreSQL remains authoritative after synchronization.
Hardware access is isolated behind Flutter platform/adapters.
Financial workflows use deterministic local transaction envelopes and server reconciliation.
Every screen must remain usable during temporary network loss where the business process permits.
2. Architecture Principles
Offline-first by default for core shop operations.
Local writes are transactional and immediately visible to the operator.
All synchronized financial operations carry a stable client transaction ID and idempotency key.
Never silently overwrite authoritative server state.
Never use floating-point arithmetic for money, weight, quantity or tax-sensitive calculations.
Sensitive secrets and SQLCipher keys never live in ordinary SharedPreferences.
UI widgets do not directly access SQLite, REST, WebSocket, or hardware.
Business rules are represented in application/domain services and shared with backend contracts through explicit schemas, not copied ad hoc.
Finalized invoices are immutable; corrections use returns/refunds/reversals.
Hardware failure never invalidates a committed invoice.
Every sync failure is visible, actionable and retryable.

5. Application Layers
6. State Management
Use Riverpod providers/notifiers or an equivalent disciplined state-management architecture.
Separate ephemeral UI state from durable business state.
Cart state may be local and session-oriented; finalized invoice state is durable.
Sync queue state is persisted, not held only in memory.
Loading/error/success/empty/offline states must be explicit.
Providers must not perform hidden writes during widget build.
Dispose stream/subscription resources correctly.
Do not create one giant global provider containing the whole application.
7. Navigation & Route Guards
Public routes: login, device registration/setup, recovery flows.
Authenticated routes: dashboard, POS, customers, inventory, procurement, reports, settings.
Permission guards must be evaluated before protected route entry and again before sensitive mutations.
Unsaved POS cart state must be protected when navigating away.
Deep links must not bypass tenant/device authorization.
Logout clears active authenticated session state and sensitive in-memory data.
8. Authentication & Device Security
Access tokens are short-lived; refresh/session credentials are stored securely.
Bind sessions to registered device identity where backend policy requires it.
Store SQLCipher encryption key only in OS secure storage or a securely derived protected mechanism.
Do not log access tokens, refresh tokens, PINs or database keys.
Support device revocation and forced re-authentication.
Optional device biometric/app lock may protect local access, but it does not replace server authorization.
Detect unsupported/rooted/jailbroken environments according to tenant policy; do not rely on client detection as the only security boundary.
On logout/revocation, clear or invalidate sensitive local session material while retaining only policy-approved offline data.
9. SQLCipher Local Database
The local database is the operational offline cache/store and must be encrypted at rest.
Use SQLCipher-compatible SQLite implementation.
Encryption key is generated/provisioned securely and never hardcoded.
Run local schema migrations transactionally.
Use DAOs/repositories rather than raw SQL from UI code.
Keep local records tenant/device scoped.
Include server IDs, local IDs, versions, sync status and timestamps where synchronization requires them.
Persist transaction envelopes separately from ordinary cached master data.
Protect database backup/export functionality; do not expose raw SQLCipher files casually.
10. Local Data Categories
11. Local Transaction Envelope
Every offline-capable mutation should be represented conceptually as:
transactionId
deviceId
tenantId
userId
operationType
schemaVersion
clientCreatedAt
idempotencyKey
payload
payloadHash
status
attemptCount
lastAttemptAt
lastErrorCode
serverEntityId
serverVersion

The envelope is immutable after creation except for synchronization metadata.
Generate transactionId with collision-resistant IDs.
Use a canonical serialized payload for hashing.
Never regenerate an idempotency key on retry.
Retrying the same envelope must produce the same server operation.
12. Repository Offline-First Strategy
Repositories decide whether data is read from local SQLCipher, remote API, or both.
Reads: local-first for low-latency screens; refresh from server when online.
Writes: local transactional queue for supported offline operations; remote-first only where business policy requires online authorization.
After server acceptance, reconcile local provisional state with authoritative IDs/versions.
Do not expose whether a source was local or remote unless the UI needs a freshness/status indicator.
Repository methods return domain models, not raw DTOs.
13. Synchronization Engine
Detect network availability and start a guarded sync cycle.
Acquire a single-device sync lock to prevent duplicate concurrent cycles.
Upload pending envelopes in deterministic order.
Process server response as accepted, duplicate, conflict or rejected.
Mark accepted envelopes with server identifiers/version.
Fetch server changes using tenant/device/user-authorized cursor.
Apply downloads transactionally to local SQLCipher.
Resolve nonfinancial master-data changes automatically when safe.
Surface financial/inventory conflicts for explicit resolution.
Persist cursor only after the corresponding page is successfully applied.
Release sync lock and update sync status.
14. Sync Connectivity Rules
Connectivity status is only a hint; successful authenticated API traffic is the real online test.
Do not start unlimited retry loops when offline.
Use exponential backoff with jitter.
Respect server Retry-After responses.
Pause sync when authentication is invalid until re-authentication succeeds.
Do not duplicate uploads after app restart.
Foreground resume should trigger a guarded sync.
Manual 'Sync Now' must not create parallel sync workers.
15. Conflict Resolution
16. POS Architecture
POS is optimized for touch, keyboard/scanner and rapid repeated transactions.
Product search supports barcode, Tamil Unicode, transliteration, aliases and colloquial terms.
Cart lines store product ID, UOM, quantity, unit price, discount, tax profile and batch allocation metadata as applicable.
Loose feed quantity is decimal and can be populated by scale reading.
Pricing tier is resolved from customer selection and effective price configuration.
Credit/Khata selection triggers local policy checks and server reconciliation.
Multi-tender supports cash + UPI + Khata subject to business rules.
Invoice finalization creates one immutable transaction envelope.
Printing occurs after commit and is independent of financial success.
17. Tamil Search UX
Search field accepts Tamil and Latin transliteration.
Normalize Unicode, punctuation, whitespace and common variants.
Display alias/product confidence and primary product name.
Support farmer shorthand without changing the canonical product name.
Barcode scan bypasses fuzzy search and directly resolves exact barcode.
Search results should remain fast from the local indexed catalogue.
Ambiguous fuzzy results require operator confirmation.
18. Weighing Scale Architecture
Create a WeighingScaleAdapter interface.
Adapters may use Bluetooth, USB serial, RS-232 or supported platform bridges.
Normalize incoming readings into decimal weight + unit + stability flag + timestamp.
Handle noisy readings with configurable stabilization/debounce.
Display connection state and last valid reading.
Allow manual entry only according to permission/policy.
Record scale source when weight materially affects a transaction.
Hardware timeout must not freeze the POS UI.
19. Barcode Scanner Architecture
Support camera scanning and hardware keyboard-wedge scanners.
Normalize scanned strings and strip configured control characters.
Debounce duplicate rapid scans.
Resolve exact product barcode locally first.
Unknown barcode produces a clear action: search/register/scan again.
Never map an unknown barcode to a fuzzy product automatically.
20. ESC/POS Printer Architecture
Create a PrinterAdapter interface with discovery, connect, print and status methods.
Generate ESC/POS bytes in a receipt renderer independent of transport.
Support USB/Bluetooth/network transports as configured.
Queue print jobs locally when appropriate.
Use idempotent print-job IDs to prevent accidental duplicate prints where feasible.
Printer failure never rolls back an already finalized invoice.
Offer reprint from the invoice screen.
Offer one-tap 'Send receipt via WhatsApp' fallback.
Receipt layout must support Tamil text through compatible printer/font strategy or image/raster rendering where necessary.
21. Payment & UPI UX
Create payment intent before presenting dynamic QR where supported.
Display pending/paid/failed/expired state.
WebSocket updates are advisory; the app can poll authoritative payment status.
Do not mark a payment permanently paid from a client callback alone.
Handle delayed payment confirmation after the POS screen changes.
Payment cancellation/expiry must be explicit.
UPI + cash split must reconcile exactly to invoice total.
Provider transaction IDs are stored for reconciliation.
22. Khata & Credit UX
Show available credit, outstanding amount and credit limit before finalization.
Warn when limit would be exceeded.
Owner/admin override requires secure PIN and permission.
Show override reason entry.
Receipt screen must show amount applied to Khata.
Customer ledger view distinguishes sales, receipts, contra credits, adjustments and reversals.
Offline balances display freshness timestamp where applicable.
23. GRN / Procurement UX
PO selection or direct receiving according to permission.
Truck/arrival metadata.
Bag count and package details.
Gross/tare/net capture.
Per-product tare configuration and threshold warning.
Net weight cannot be negative.
Excess tare requires correction or authorized override with reason.
Batch number, manufacture/expiry dates where applicable.
Finalization creates local transaction and later server reconciliation.
24. Inventory UX
Display sealed bags and loose quantity separately when UOM model requires it.
Batch-aware stock display.
FIFO/FEFO allocation visibility where operationally useful.
Expiry/aflatoxin alert badges.
Stock count workflow requires reason and authorization.
Stock adjustment screen must show before/after quantity and reason.
Never permit silent deletion of stock.
25. Returns & Refund UX
Select original invoice where available.
Validate returnable quantity against prior returns.
Return stock to the correct batch/location according to policy.
Choose refund mode: cash/UPI/credit/Khata reversal where permitted.
Finalized return is immutable.
Refund provider operation is asynchronous and independently reconciled.
Print/send return receipt after successful internal commit.
26. EOD / Cash Closure UX
Open cash session with opening float.
Record cash movements/payouts.
Calculate expected cash from authoritative local transaction set.
Enter physical cash count.
Show variance prominently.
Require reason/approval for configured variance threshold.
Finalize EOD as immutable session result.
Sync EOD result to server and show reconciliation status.
27. Reports & Dashboard
Dashboard cards should distinguish local cached values from fresh server values where relevant.
Heavy reports use server-side async jobs.
Offline mode shows only supported cached/operational reports.
Exports display job progress and final file availability.
All report filters include tenant scope implicitly.
28. Notifications & Reminders
Use local notifications for expiry, collection and operational reminders where permitted.
Server remains authoritative for scheduled reminders and deduplication.
Aavin/payment-cycle reminder dates and grace periods are configurable.
Pause dates and duplicate prevention are supported.
Notification content is localized.
29. Localization
Support Tamil and English from the architecture level.
Use localization resource files; never scatter user-facing strings through code.
Numbers, currency, date/time and weights use locale-aware formatting.
Preserve Tamil Unicode in storage, search and printing.
Allow tenant-preferred language with user-level override if permitted.
Do not translate product master values automatically.
30. Accessibility & Shop Usability
Large touch targets for POS.
High-contrast status indicators.
Keyboard navigation for desktop-like devices where supported.
Readable numeric typography for weights and totals.
Clear online/offline/sync state.
Minimal modal interruptions during rapid sales.
Confirm destructive/sensitive operations.
Use vibration/sound feedback for successful scans where device policy allows.
31. Error & Recovery UX
32. Networking Layer
Centralize REST configuration in a typed API client.
Attach Authorization, X-Request-ID, Idempotency-Key, X-Device-ID, X-App-Version and Content-Type as required by the API.
Use interceptors for authentication refresh, request IDs and safe logging.
Map HTTP errors to typed domain/application errors.
Use bounded timeouts for connect, send and receive.
Support cancellation for search and report requests.
Do not retry non-idempotent operations unless protected by idempotency.
33. API DTO Mapping
Keep generated/transport DTOs separate from domain entities.
Validate required fields during decoding.
Preserve decimal values without converting to binary floating point.
Preserve unknown server fields where forward compatibility requires it.
Version offline payload schemas.
Never serialize internal database implementation details to the API unless contractually required.
34. Local Database Migration
Bundle migration scripts with the app version.
Read current local schema version.
Apply migrations in a transaction.
Verify required tables/indexes.
Only mark schema version after success.
Retain backward-compatible migration paths for supported upgrade ranges.
On failure, prevent normal operation rather than opening a partially migrated database.
Backup/export recovery is controlled and encrypted where supported.
35. Performance Architecture
Index local product aliases/barcodes for search.
Paginate long lists.
Debounce text search.
Use isolates/background computation for heavy parsing/export preparation.
Do not rebuild large widget trees unnecessarily.
Use const widgets where possible.
Keep POS interactions responsive under normal catalogue sizes.
Batch sync operations where API contract permits.
Avoid loading complete historical ledgers into memory.
36. Memory & Lifecycle
Dispose controllers, streams, subscriptions and hardware connections.
Pause nonessential listeners when screens are backgrounded.
Do not retain entire invoice/report datasets in long-lived providers.
Handle Android process death by restoring safe persisted state.
Persist active POS draft safely enough to recover after unexpected restart.
37. Offline Security
Encrypt SQLCipher database.
Secure encryption key with OS secure storage.
Limit locally cached PII according to tenant policy.
Apply local session timeout/app lock.
Do not trust local authorization as a substitute for server authorization.
Tag locally generated transactions with device/user identity.
On device revocation, block synchronization and sensitive operations.
Provide controlled data wipe for decommissioned devices.
38. Hardware Permissions
Request only required Bluetooth/USB/camera permissions.
Explain permission purpose to the operator.
Handle denied/restricted permissions without crashing.
Store paired-device identifiers securely.
Provide test-connection actions in settings.
Maintain hardware status independently from business transactions.
39. WebSocket Client
Authenticate WebSocket connection.
Reconnect with exponential backoff.
Discard stale events using event IDs/versions.
Never assume an event was received; REST resync remains available.
Update payment/sync status only after validating tenant/session context.
Close connection cleanly on logout.
40. Sync UI
Persistent small sync indicator: synced/syncing/offline/error.
Tap opens sync details.
Show pending count and oldest pending transaction age.
Show conflict count separately from transient retry failures.
Allow safe manual retry.
Do not expose technical stack traces to operators.
Critical unsynchronized financial transactions should be clearly identifiable.
41. Security & Privacy UX
Mask sensitive identifiers where practical.
Confirm owner/admin actions.
Do not display secret credentials.
Warn before clearing local data.
Show device registration status.
Provide audit-friendly confirmation for high-risk operations.
42. App Configuration
Secrets must not be embedded as permanent client credentials. Provider secrets belong on the backend.

49. App Update & Compatibility
Backend supports the declared range of app schema versions.
Local migrations run before normal startup.
Critical security updates may require minimum app version enforcement from server.
Offline users should receive a clear upgrade-required state when the backend no longer supports their version.
Never invalidate an already-finalized local transaction solely because a newer UI version exists.
50. Crash & Diagnostics
Capture crash, app version, device model, OS version and non-sensitive diagnostic context.
Associate errors with request IDs where available.
Do not capture tokens, SQLCipher keys, PINs or unnecessary PII.
Provide operator-safe diagnostic export only with authorization.
Track sync failures separately from app crashes.
51. Feature Flags
Flags may control staged features such as new POS layouts, optional hardware support or experimental search.
Financial correctness must not depend on an unstable client-only feature flag.
Server can disable incompatible features remotely.
Every flag has an owner, default, rollout policy and removal plan.
52. Backup / Recovery of Local State
Server remains the recovery source for synchronized transactions.
Unsynchronized transaction envelopes are critical local recovery data.
Provide safe app restart recovery without exposing the raw database.
Do not rely on consumer cloud backup for SQLCipher keys unless explicitly designed and tested.
Decommissioned devices must have a controlled local-data wipe procedure.

59. Final Architecture Summary
The Flutter application is an offline-first shop edge application with a clean separation between presentation, application/domain logic, repositories, encrypted local persistence, remote API integration, synchronization and hardware adapters. Core shop workflows continue safely through connectivity interruptions, while PostgreSQL remains the final authority. Local financial operations are represented as immutable transaction envelopes with stable IDs and idempotency. Hardware failures are isolated from financial finalization, and Tamil/local-language search is a first-class capability.

Appendix B — Acceptance Scenarios
Product can be found offline using Tamil alias and transliteration.
Barcode scan adds the correct product without network.
Loose feed sale captures stable decimal scale weight.
App restart preserves an unfinished POS cart according to policy.
Offline finalized sale remains visible and prints even with no network.
