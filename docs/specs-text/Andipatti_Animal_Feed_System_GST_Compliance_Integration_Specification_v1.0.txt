1. Document Control
2. Purpose & Scope
This document defines how the system determines, snapshots, validates, records, exports and integrates GST/compliance information for animal-feed retail/wholesale transactions. It covers product tax configuration, HSN/tax codes, CGST/SGST/IGST handling, tax-inclusive/exclusive prices, invoices, credit/debit adjustments, returns, e-invoice integration where applicable, e-way bill workflows where applicable, GST reports/exports, auditability, compliance jobs and archival.
Support configuration-driven tax treatment.
Preserve historical tax snapshots on finalized documents.
Support intra-state and inter-state tax treatment where applicable.
Support tax-exempt/zero-rated/non-taxable classifications where configured.
Support compliance-provider integration without coupling core POS to a single provider.
Produce reconciliation-ready GST data.
Never hardcode current legal thresholds or rates into application logic.
3. Non-Goals
The application does not decide legal applicability from outdated assumptions.
It does not replace a tax professional or government portal.
It does not silently alter historical invoices when tax masters change.
It does not treat an API provider response as valid without authentication, validation and traceability.
It does not delete compliance evidence during ordinary archival.
4. Compliance Architecture Principles
Tax determination is a versioned domain service.
Product tax configuration is effective-dated.
Finalized documents store the exact tax snapshot used.
Tax calculations use decimal arithmetic.
Government/provider integrations are adapters behind stable interfaces.
External calls are asynchronous where they do not need to block transaction finalization.
Compliance documents and responses are immutable evidence records.
All compliance requests are idempotent.
Every adjustment links to its source document.
Reports are reproducible from authoritative transaction data.
Rule changes are versioned and tested before activation.
5. Compliance Domain Model
6. Tax Master Data
A tax profile must be validated for internal consistency. For example, a profile intended for an intra-state split must not simultaneously produce an unrelated IGST calculation for the same taxable line.
7. HSN / Product Tax Classification
Product master stores HSN/tax classification reference as configured.
Classification changes are effective-dated.
Historical invoices retain the HSN/tax snapshot used at finalization.
Missing HSN for a transaction requiring it is a configurable validation error.
Product archival does not remove historical HSN data.
Bulk imports require validation and approval before activation.
The system should distinguish between a product's master HSN value and the finalized invoice's HSN snapshot.
8. Place of Supply & Tax Type
Determine seller/tenant registration state from tenant configuration.
Determine customer/transaction state from validated customer/address/transaction data where required.
Apply configured place-of-supply logic.
Determine intra-state versus inter-state treatment only through the tax rules engine.
Do not infer tax treatment from a free-text address.
Business exceptions require explicit tax-rule configuration and audit.
The exact legal place-of-supply rule depends on transaction facts and applicable law; the software therefore models the rule rather than hardcoding a simplistic state comparison for every scenario.
9. Tax Calculation
Line:
gross = quantity × unit_price
discount = approved line/invoice allocation
taxable_value = applicable_tax_base(gross, discount, adjustments)

If tax-exclusive:
tax = taxable_value × rate

If tax-inclusive:
taxable_value = reverse_calculate_tax(inclusive_amount, rate)

Tax components:
CGST + SGST + IGST + CESS/other configured components

Invoice tax = sum of applicable tax lines

All calculations use decimal arithmetic.
Tax calculation strategy is explicit and versioned.
Rounding strategy is configured and consistent with accounting/export.
Do not double-tax an amount.
Discount treatment follows the configured tax rule.
Rounding differences are explicitly represented where needed.
10. Tax-Inclusive Pricing
Store whether price is tax-inclusive or tax-exclusive.
For inclusive prices, reverse-calculate taxable base and tax using the configured rate/rounding policy.
Displayed unit price must remain understandable to cashier/customer.
Final invoice stores both price basis and resulting tax values.
Changing a product's tax-inclusion setting does not rewrite old invoices.

15. GSTIN Validation
GSTIN format validation is a first-line input check, not proof of registration status.
Where a verified GSTIN lookup provider/API is used, store verification status, timestamp and source.

17. E-Invoice Architecture
Where e-invoicing is legally applicable to the tenant/transaction, integrate through the currently authorized government/ASP/GSP interface.
Determine applicability using effective-dated tenant/transaction configuration and current compliance rules.
Validate mandatory invoice fields.
Create idempotent e-invoice request.
Submit through provider adapter.
Validate response and authenticity.
Store IRN/acknowledgement/status and required signed/encoded artifacts.
Link compliance document to internal invoice.
Expose status to authorized users.
Handle cancellation/update only through supported official workflow and time/rule constraints.
Reconcile provider records with internal invoices.
The exact applicability threshold, schema, API version, cancellation window and required fields must be externally maintained and revalidated before production deployment.

60. Non-Negotiable Compliance Rules
Never hardcode tax rates or legal thresholds that are expected to change.
Never rewrite historical tax snapshots when masters change.
Never use floating-point arithmetic for tax or money.
Never create a second e-invoice merely because the first request timed out.
Never trust an unsigned/unverified compliance callback.
Never treat provider timeout as automatic failure or success.
Never delete compliance evidence merely because a document is archived.
Never allow tax master changes to bypass effective dating and audit.
Never finalize a tax-sensitive transaction without required tax configuration.
Never allow period lock to be bypassed by ordinary cashier operations.
Never let offline cached tax data silently override authoritative server policy.
Never edit finalized invoices to correct tax; use controlled adjustment documents.
Never use a single hardcoded e-way applicability threshold as the universal rule.
Never expose government/provider credentials in Flutter or logs.
Never allow cross-tenant access to compliance documents or exports.
