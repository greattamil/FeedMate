Document 09 — Complete Hardware Integration Specification v1.0
Implementation-ready specification • Flutter Edge Device • Go Backend • Docker • Offline-first • POS-integrated
Document sequence: 09 of 20 | No sprint planning
This document defines the hardware boundary for barcode scanners, digital weighing scales, ESC/POS printers, cash drawers, customer/payment displays and related POS peripherals. Hardware is an edge concern: Bluetooth/USB/RS-232 device access stays on the Flutter device, while authoritative business state remains in the Go/PostgreSQL platform.
1. Document Control
2. Objectives
Provide a vendor-neutral hardware abstraction layer.
Support USB, Bluetooth/BLE and RS-232 serial peripherals where appropriate.
Support barcode scanners as keyboard-HID and serial devices.
Support digital weighing scales with stable-weight validation.
Support ESC/POS thermal printers and common connection modes.
Support cash-drawer triggering through printer RJ-12/RJ-11 kick interface where available.
Support optional customer-facing display and payment/QR display.
Persist pairing/configuration per device and tenant.
Provide diagnostics, health state, reconnection and controlled fallback.
Keep hardware I/O outside authoritative accounting/inventory transactions.
Make all device actions observable and auditable without logging secrets.
3. Non-Goals
Do not run Bluetooth/USB hardware drivers inside backend Docker containers.
Do not make a printer, scale or scanner a prerequisite for server-side invoice finalization unless a specific business rule explicitly requires the scale for a weighted item.
Do not store raw payment credentials in hardware adapters.
Do not infer weight, payment success or print success from UI state alone.
Do not silently switch hardware devices without an explicit pairing/configuration policy.

5. Hardware Device Registry
Hardware configuration changes require authorization.
Device pairing must be tenant-scoped.
Revoked POS devices must not perform authoritative financial operations.
Sensitive Bluetooth/USB permissions remain OS-controlled.
6. Hardware Capability Matrix
7. Common Connection State Machine
Automatic reconnect must use bounded exponential backoff.
Reconnect attempts must not freeze the POS UI.
Only one active adapter instance may own a physical device per terminal.
Connection events are observable and locally visible to authorized operators.
8. Barcode Scanner Integration
8.1 Supported modes
USB HID keyboard-wedge.
Bluetooth HID.
Serial/COM scanner where supported.
Vendor SDK only behind a scanner adapter when generic protocols are insufficient.
8.2 Scan processing
Receive scanner input.
Detect configured terminator/prefix/suffix.
Normalize whitespace and control characters.
Validate barcode length/format according to product configuration.
Resolve exact barcode locally or through API.
Present product selection to POS.
Apply configured duplicate-scan behavior.
Record device and timestamp for diagnostics.
8.3 Duplicate scans
Rapid identical scans may intentionally increase quantity for countable products.
Weighted/loose products must follow product-specific scan behavior and must not multiply a scale reading unexpectedly.
Configurable debounce interval prevents accidental repeated input.
Manual correction remains available.
8.4 Unknown barcode
Display explicit unknown-barcode status.
Allow search by Tamil/English/alias/product code.
Never auto-create a product from scanner input.
Authorized users may open product-master workflow.
9. Digital Weighing Scale
9.1 Supported transports
RS-232 serial.
USB-to-serial adapters presenting a serial interface.
Bluetooth serial profile where supported by the device.
BLE only when a documented vendor protocol exists.
9.2 Configuration
Defaults must be configured per hardware model/protocol. Never assume a universal serial configuration.
9.3 Scale reading pipeline
RAW BYTES
 -> FRAME DETECTION
 -> CHECKSUM/VALIDATION (if protocol supports)
 -> PARSE SIGN + VALUE + UNIT + STATUS
 -> UNIT CONVERSION
 -> RANGE VALIDATION
 -> STABILITY FILTER
 -> STABLE WEIGHT EVENT
 -> POS WEIGHT SERVICE
 -> CART LINE
 -> FINALIZATION REVALIDATION
9.4 Stable-weight rules
A stable reading requires the configured duration and variance criteria.
Scale status flags such as overload, motion, negative or error must be rejected.
Zero/negative readings cannot finalize a normal positive-weight sale.
Automatic acceptance must use a stable event, not an arbitrary latest frame.
Manual weight entry is permission-controlled and audited.
At finalization, the backend validates the quantity against product/UOM rules; it does not trust a client-side stability flag as a financial authority.
10. Scale Safety & Tare
Gross, tare and net concepts must remain distinct where the weighing workflow uses them.
Where procurement/GRN uses sack tare, the GRN engine validates tare separately from POS.
POS weighted sales generally consume net sale quantity.
Scale overload must immediately stop automatic capture.
An operator must not be able to enter a negative net weight.
Any manual tare adjustment is explicitly recorded and permission-controlled.
11. Scale Protocol Adapter Contract
interface ScaleAdapter {
  connect(config) -> Result
  disconnect() -> Result
  readLive() -> Stream<ScaleReading>
  requestStableReading() -> Result<StableWeight>
  zero() -> Result
  tare() -> Result
  diagnostics() -> Result<ScaleDiagnostics>
}

The exact Dart interface may differ, but the semantic contract must remain equivalent. Backend services never directly depend on the physical protocol.
12. Thermal Printer / ESC-POS
12.1 Supported transports
USB serial/USB printer interface.
Bluetooth serial where supported.
RS-232/serial.
Network/TCP printing where the printer supports it.
12.2 Printer responsibilities
Render finalized receipt content into an ESC/POS command stream.
Handle paper width and character capability.
Print Tamil through supported font/bitmap/image rendering where native code-page support is unavailable.
Support barcode/QR printing when printer supports it.
Support cash-drawer kick where configured.
Return print status/errors where the transport provides them.
12.3 Print pipeline
Retrieve finalized invoice receipt snapshot.
Resolve printer profile.
Render layout.
Encode Tamil/Unicode using configured strategy.
Generate ESC/POS command stream.
Open transport.
Write with bounded timeout.
Flush/close.
Record print attempt.
Expose success/failure to UI.
Printing occurs after financial commit. A print exception must never roll back the invoice.
13. Tamil Printing
Preferred method: printer-supported Unicode/font rendering.
Fallback: render Tamil receipt text as raster image/bitmap if printer cannot render required Unicode.
Printer profile stores supported character strategy.
Golden receipt tests must verify Tamil output on each supported printer profile.
Do not silently replace Tamil with unrelated glyphs.
If Tamil cannot be printed reliably, offer WhatsApp/PDF/digital receipt fallback according to configured capabilities.
14. Receipt Layout Requirements
15. Reprint & Print Retry
Reprint is always based on finalized invoice data.
Reprint permission is role-controlled.
Each reprint creates an audit event.
Retry is safe because printing is an external side effect.
Print attempt IDs prevent duplicate operational records but do not prevent legitimate reprints.
Printer recovery should allow retry without reopening or editing the invoice.
16. Cash Drawer
Preferred trigger: ESC/POS cash-drawer kick from printer.
Drawer opening occurs only for configured cash operations.
Opening event records user, terminal, timestamp and reason where applicable.
Drawer-open failure does not alter invoice/payment state.
Physical cash reconciliation remains part of cash session/EOD.
Do not expose drawer control to unauthorized roles.
ESC/POS concept:
ESC p m t1 t2
(Exact bytes depend on printer and configured kick parameters.)
17. Customer Display
Show cart lines, quantities, price, discount and total.
Show tax only as configured.
Show payment amount/QR when payment workflow requires it.
Do not display sensitive Khata exposure, internal cost, margin or owner-only data.
Display connection loss without blocking the POS workflow.
18. Payment/QR Display
QR content originates from the payment provider/payment intent, not from manually typed arbitrary data.
Display may be a second monitor, network display, serial display or Flutter screen.
Payment display is informational; provider verification remains authoritative.
Do not mark payment successful from QR display interaction.
19. Hardware Pairing & Provisioning
Admin identifies terminal.
Discover or enter hardware.
Select hardware type and protocol profile.
Pair/connect through supported OS mechanism.
Run diagnostics test.
Save configuration.
Record device identity.
Run test scan/weight/print.
Mark device ACTIVE.
Provisioning must validate tenant and terminal ownership.
Device configuration changes are audited.
Secrets/credentials, if any, use secure storage or environment/secret-management mechanisms.
20. Diagnostics Mode
Diagnostic mode must never create inventory, accounting, payment or invoice transactions.
21. Hardware Health Model
Health data should be retained according to operational observability/retention policy and should not grow without bounds.
22. Failure Isolation Rules
Hardware adapter exceptions are caught at the edge boundary.
A printer exception never rolls back an invoice.
A scanner failure never blocks manual search.
A scale failure only blocks automatic weighted capture; authorized manual entry may be allowed.
Customer-display failure never blocks billing.
Payment-display failure never changes payment state.
Hardware reconnect runs asynchronously.
Hardware event streams must be cancelled on screen/device lifecycle changes to avoid leaks.
23. Offline Hardware Operation
Scanner works against local SQLCipher product index.
Scale can capture weights offline.
Printer can print local finalized/provisional receipts according to offline receipt policy.
Hardware events can be stored with local transaction envelope IDs.
On reconnect, hardware telemetry does not override authoritative financial data.
Offline provisional receipt must be clearly distinguishable if local policy requires it.
24. Hardware + POS Transaction Boundary
Hardware event
   -> local POS state
   -> user confirmation
   -> POS quote
   -> payment workflow
   -> server finalization
   -> committed invoice
   -> post-commit print/share

Never:
hardware event -> direct DB financial write
printer success -> invoice finalization
QR display -> payment success
scale "stable" flag -> unconditional stock decrement

29. Security
Only authenticated, authorized users can configure hardware.
Device IDs are authenticated and tenant-bound.
Revoked devices are rejected server-side.
USB/Bluetooth permissions follow OS security model.
Hardware debug logs must not expose secrets.
Payment QR payloads are treated as payment data and are not logged in full unless explicitly required and protected.
Receipt data follows privacy policy; avoid unnecessary PII in diagnostics.
Admin-only diagnostics may expose raw protocol data where operationally necessary, with controlled retention.
Firmware update capability, if later added, must use signed/verified firmware and a separate security specification.

32. Reconnection & Retry Policy
Use exponential backoff with jitter, e.g. 1s, 2s, 4s, 8s, capped at a configured maximum.
Reset retry counter after stable successful connection.
Do not retry malformed protocol commands indefinitely.
Do not retry printer jobs automatically if doing so could produce duplicate physical prints unless the transport provides an acknowledgement model; expose manual retry instead.
Scale continuous read streams may reconnect automatically.
Payment operations must use payment-service idempotency, not hardware retry semantics.
33. Printer Duplicate-Print Safety
Printing is inherently difficult to make exactly-once because a connection can fail after the printer physically receives bytes. Therefore:
Each print attempt has a local print_job_id.
On uncertain completion, UI shows UNKNOWN/REQUIRES_RETRY rather than assuming failure.
Automatic retry is disabled for uncertain receipt jobs unless the printer/transport provides reliable job acknowledgement.
Manual retry is allowed and is an audited reprint if the invoice was already finalized.
Financial state never depends on print acknowledgement.
34. Scale Duplicate/Replay Safety
Every accepted stable weight has a local capture ID.
POS associates the capture ID with cart line/version.
Re-reading a scale creates a new capture ID.
An old capture cannot silently replace a newer confirmed weight.
At finalization, the quantity sent to the backend is validated against the current cart line and product/UOM rules.
35. Customer Display Consistency
Display is derived from current POS presentation state.
Display update failures do not mutate the authoritative cart.
During payment, the displayed amount must come from the same calculated quote shown to the cashier.
After finalization, display may show completion/thank-you state but must not reveal internal audit information.
36. Hardware Configuration Versioning
Every configuration has a version.
Changing baud rate, protocol profile, paper width, encoding mode, stability rules or device assignment increments configuration version.
Local Flutter cache stores the active version.
Server configuration wins for authoritative provisioning.
Config changes are auditable.
Rollback to a prior known-good configuration is supported for authorized operators.
37. Localization & Accessibility
Hardware setup screens support Tamil and English.
Use clear icons plus text for connection state.
Do not rely on color alone to communicate errors.
Scale weight must use large, readable typography.
Printer/scale failure messages should state the next action.
Touch targets must be suitable for shop-floor use.

46. Data Retention & Privacy
Retain device configuration and audit according to operational retention policy.
Do not retain raw scanner input longer than needed unless diagnostic policy requires it.
Raw scale frames should normally be diagnostic-only and short-retention.
Receipt copies follow invoice/document retention policy.
Hardware logs must be scrubbed of tokens, payment secrets and unnecessary PII.
47. Firmware & Updates — Future Extension
Firmware updates are outside the v1.0 POS hardware control path.
If introduced, firmware must be signed, version-checked and rollback-capable.
Only authorized administrators may initiate updates.
Power-loss recovery must be designed before enabling production firmware updates.
Firmware version is informational in v1.0 unless a device compatibility rule explicitly requires it.

50. Non-Negotiable Hardware Rules
Never allow physical hardware success to be the authority for a financial transaction.
Never allow printer failure to roll back a finalized invoice.
Never trust a scale stability flag without backend/POS quantity validation.
Never accept negative, overload or invalid weight as a normal sale quantity.
Never auto-create products from scanner input.
Never use hardware adapters directly from accounting/inventory code.
Never perform Bluetooth/USB/RS-232 physical I/O from backend Docker containers.
Never retry an uncertain printer job automatically in a way that can silently duplicate a receipt.
Never expose payment secrets in hardware logs.
Never let customer display/payment display determine payment settlement.
Never allow revoked devices to perform authoritative operations.
Never bypass audit for manual weight, reprint, drawer operation or hardware configuration.
Never hardcode a single serial protocol configuration for all scales.
Never assume all printers support Unicode/Tamil natively; use a tested fallback rendering strategy.
51. End-to-End Hardware Scenarios
51.1 Barcode cash sale
Scanner reads barcode.
POS resolves product.
Cashier confirms quantity.
POS calculates quote.
Cash accepted.
Server finalizes invoice.
Post-commit printer prints.
Drawer kick occurs if configured.
51.2 Loose feed by scale
Cashier selects loose product.
Scale streams readings.
Stable reading accepted.
POS associates capture ID.
Quote calculated.
Payment completed.
Server finalizes stock/accounting.
Receipt prints.
51.3 Scale disconnected
Disconnect detected.
POS preserves cart.
Cashier reconnects or uses authorized manual weight.
Manual entry reason recorded.
Finalization performs normal server validation.
51.4 Printer fails after sale
Invoice commits.
Printer write fails.
Invoice remains FINALIZED.
Cashier retries or shares via WhatsApp.
Audit records print/share outcome.
51.5 Uncertain print
Printer transport times out after bytes may have been delivered.
POS marks print outcome UNKNOWN.
No new invoice is created.
Operator checks physical printer.
Operator uses controlled reprint if required.
51.6 Offline sale
Scanner/scale work locally.
Sale is stored in SQLCipher envelope.
Local receipt follows offline policy.
Network returns.
Envelope uploads idempotently.
Server reconciles inventory/credit/price policy.
Authoritative result is returned.
