Document 05 — Complete Offline-First & Synchronization Specification
v1.0 — Implementation Baseline
Aligned with PRD v1.2, Database & ERD v1.0, API Specification v1.0, Go Backend Technical Architecture v1.0, and Flutter Technical Architecture v1.0.
This document defines the exact client synchronization model for unreliable connectivity, including SQLCipher local persistence, transaction envelopes, upload/download queues, cursors, idempotency, conflicts, retries, reconciliation, recovery and operational visibility.
1. Objectives
Allow core shop workflows to continue safely during internet outages.
Never lose a locally committed supported transaction because the app is closed or restarted.
Ensure every transaction reaches the backend at most once in business effect, even if transmitted many times.
Keep PostgreSQL authoritative while preserving a durable local pending queue.
Prevent cross-tenant and cross-device data leakage.
Provide deterministic, auditable conflict handling.
Support delayed payment confirmations and external side effects without corrupting invoices.
Make synchronization observable to the shop operator and support team.
2. Source of Truth Model
The client may act on cached information only within explicitly permitted offline policies. It must not represent cached state as authoritative when freshness matters.
3. Offline Capability Classes
Each operation must declare its offline capability explicitly; developers must not infer it from whether an endpoint happens to be reachable.

5. Local Sync Database Model
Exact physical columns must remain aligned with the database specification and Flutter implementation. All local tables are SQLCipher protected.
6. Local Transaction States
7. Local Database Transaction Rules
Start SQLite transaction.
Validate local business invariants.
Write business data/provisional projection.
Create immutable sync transaction envelope.
Update local sync metadata.
Commit SQLite transaction.
Only after commit may the UI show the operation as locally finalized.
Sync runs separately and must never depend on the original UI isolate remaining alive.
If any step before local commit fails, no partial business transaction may remain.
8. Upload Queue Algorithm
Select eligible READY transactions for the authenticated tenant/device.
Exclude transactions whose dependencies are not terminally accepted.
Acquire local sync lock.
Mark selected transaction as UPLOADING.
Send envelope with idempotency key.
Validate server response signature/shape according to API contract.
On ACCEPTED, persist server ID/version and authoritative snapshot.
On DUPLICATE, persist original server result and reconcile.
On CONFLICT, persist conflict without destructive local overwrite.
On REJECTED, preserve transaction and actionable error.
Commit local result.
Continue according to retry/backoff policy.
9. Upload Ordering
Prefer creation order for independent financial transactions.
Honor explicit depends_on relationships.
Do not upload a receipt before its associated local sale if the receipt is represented as a dependent business event.
Do not upload a payment allocation that requires a server invoice until the invoice has an authoritative ID.
Master-data updates from the server may be applied independently when safe.
Ordering is a correctness mechanism, not merely a performance preference.
10. Download / Pull Algorithm
Authenticate and request changes from the last persisted cursor.
Receive a bounded page of changes plus next cursor.
Validate tenant/scope and schema.
Apply changes to SQLCipher in one local transaction.
Preserve local pending mutations and resolve versions according to conflict policy.
Commit the page.
Persist the next cursor only after successful commit.
Request next page until complete or server limits are reached.
Never advance a cursor when the page was only partially applied.
11. Cursor Model
Cursors are opaque server-issued values. The client must not parse, modify, or manufacture cursor contents.
Cursor scope includes tenant and authorized device/user context.
Separate cursors may exist for master data and operational events.
Cursor storage is durable and encrypted.
Cursor reset requires a controlled full/partial resync.
Expired/invalid cursors return a documented recovery response.
After cursor reset, the client rebuilds the relevant local projection without deleting unsynchronized financial envelopes.
12. Server Change Versioning
Use monotonically comparable server versions or event sequence numbers within each synchronization scope.
Every downloaded entity/event carries enough version metadata to reject stale updates.
Do not use client timestamps as authoritative ordering.
Server commit order is authoritative for conflicting server changes.
13. Idempotency Rules
The local queue must assume that every network timeout may mean 'server committed but client did not receive the response'.
14. Conflict Taxonomy
15. No Last-Write-Wins Rule
Last-write-wins is prohibited for finalized invoices, payments, stock movements, customer ledger, supplier ledger, accounting journals, EOD closure, returns/refunds and other financial records. Corrections are new transactions or reversals. Last-write-wins may be considered only for explicitly nonfinancial presentation preferences where documented.
16. Offline Pricing
Store the exact price/tax configuration snapshot required by the offline sale policy.
Record price-list ID/version and effective timestamp.
At server acceptance, validate whether offline pricing is still permitted.
If policy permits, preserve the originally authorized offline price.
If policy does not permit, route to conflict before final financial acceptance.
Never silently change the displayed final price after the customer has completed payment.
17. Offline Tax Handling
Tax profiles are cached with effective dates/version.
Calculations use decimal-safe arithmetic.
Tax configuration is not hardcoded in Flutter.
If a tax configuration is expired/unknown for an offline transaction, follow tenant policy: block or use an explicitly approved cached profile.
Server performs authoritative validation on synchronization.
18. Offline Inventory Policy
Because inventory is financially and operationally sensitive, the tenant must explicitly choose the supported offline policy.
Default recommendation: controlled offline with conservative safety buffer for shops that require continuity, subject to business approval.
19. Offline Credit / Khata Policy
Cache customer credit limit and last authoritative balance/version.
Allow offline credit only if tenant policy permits.
Apply local conservative limit including a safety margin.
Every offline credit sale is uploaded with the original customer/version context.
If authoritative balance differs materially, server applies conflict policy rather than overwriting ledger.
Owner PIN override is still required locally for configured threshold, but backend remains final authority.
20. Offline Payment Policy
Cash may be recorded locally as a tender according to offline policy.
Khata may be recorded as a ledger operation according to credit policy.
UPI/provider confirmation is online-authoritative unless a provider-specific offline mechanism exists and is explicitly supported.
A payment intent can remain PENDING until server/provider confirmation.
Never mark an online UPI transaction permanently PAID merely because the QR was displayed or a client callback fired.
21. Payment Reconciliation After Offline Sale
Local sale records payment tender intent/status.
On reconnect, invoice is synchronized.
Payment intent is created or reconciled on server.
Provider status is verified.
Payment allocation is posted exactly once.
WebSocket/poll updates the client.
Any mismatch is surfaced as a reconciliation exception.
22. Local Provisional IDs
Generate UUID/ULID-style local IDs for offline entities.
Server returns authoritative IDs when accepted.
Maintain local_id → server_id mapping.
Never reuse a local ID for another business transaction.
Keep mapping until retention policy permits cleanup.
23. Dependency Graph
Example: sale transaction may depend on locally created customer, product sync version, and payment intent. Dependencies are explicit only where necessary.
Prevent circular dependencies.
Reject malformed dependency graphs locally.
Transactions blocked by unresolved dependencies remain READY/BLOCKED with reason.
Dependency completion should trigger a retry without user re-entry.
24. Retry & Backoff
Use exponential backoff with jitter for transient network/server errors.
Honor Retry-After where supplied.
Do not retry validation/business-rule failures automatically without state change.
Do not retry authentication failures indefinitely.
Cap retry delay and persist next_attempt_at.
Provide manual retry for operator-visible failures.
25. Suggested Retry Classification
26. Connectivity Detection
Use OS connectivity information only as a trigger.
Confirm actual API reachability with authenticated requests.
Do not repeatedly ping the backend while offline.
Reconnect events start a debounced sync attempt.
Foreground/resume starts a sync attempt.
Manual sync is serialized with automatic sync.
27. Sync Lock
Only one upload/pull coordinator runs per device.
Persist or safely recreate lock state after process death.
Do not use a permanent lock that can survive crashes indefinitely.
Lock acquisition has a timeout/recovery mechanism.
UI may request sync but must not execute synchronization logic itself.
28. Crash Recovery
On app startup, inspect sync_transactions in UPLOADING state.
Treat them as READY unless an authoritative local marker proves terminal completion.
Retry with the same idempotency key.
Server returns ACCEPTED or DUPLICATE if it already committed.
Reconcile local state.
Resume normal queue processing.
29. Partial Failure Handling
Never mark an entire batch synchronized because one item succeeded.
Each transaction receives its own result.
Pull pages are atomic locally.
External side effects may be independently pending.
UI shows partial synchronization accurately.
30. Server Response Contract
Each synchronization response should identify transaction_id, result status, server entity ID/version where applicable, authoritative snapshot or reference, error code, safe message, conflict details where applicable, and retryability. The client must ignore undocumented fields but must not ignore status semantics.
31. Conflict Record
32. Conflict Resolution UI
Show what the operator attempted and what the server currently says.
Do not present raw JSON as the primary interface.
Use clear actions such as Retry, Accept Server State, Create Adjustment, Contact Admin.
Financial conflicts must not offer an unsafe 'force overwrite' button.
Resolution requires permission where financial impact exists.
Resolution action becomes a new auditable transaction when it changes financial state.
33. Full Resynchronization
A full resync rebuilds cached server-derived data while preserving unsynchronized local financial envelopes.
Pause normal sync.
Back up/preserve pending transaction envelopes.
Invalidate relevant cursors.
Download authoritative master/projection data in pages.
Rebuild local derived tables transactionally.
Restore pending transaction references/mappings.
Resume upload.
Reconcile results.
Mark resync complete.
34. When Full Resync Is Required
Cursor expired/invalid and cannot be resumed.
Local database corruption repaired from a known-good state.
App upgrade changes local projection incompatibly.
Tenant/device assignment changed.
Server instructs client to resync.
Detected local/server version divergence that incremental changes cannot safely resolve.
35. Local Data Retention
Retain pending and unresolved transactions until terminal resolution.
Retain enough invoice/payment/ledger metadata for supported offline recovery.
Remove obsolete cached history according to tenant policy.
Never delete a pending financial transaction merely because it is old.
Local cleanup must not affect server-authoritative data.
36. Encryption & Key Management
SQLCipher database is encrypted at rest.
Encryption key is stored in OS secure storage.
Key is not derived from a simple user PIN alone.
Key rotation, if supported, must migrate the database transactionally.
Key loss means local unsynchronized recovery may be impossible; operational recovery procedures must account for this.
Never include database keys in crash reports.
37. Tenant Isolation in Sync
Every sync request is authenticated and tenant-scoped.
Server determines permitted tenant from session/device membership.
Client-supplied tenant_id is validated, not trusted.
Cursor cannot be reused across tenants/devices if server policy prevents it.
Downloaded records are filtered by server authorization/RLS.
Client local database is treated as sensitive and should not be shared between tenants on a device without explicit secure separation.
38. Device Registration & Revocation
Each device has a stable device ID.
Device registration establishes tenant association and server permissions.
Revocation immediately prevents synchronization when detected.
Pending transactions remain locally protected but cannot upload until an authorized recovery path is established.
Device replacement requires explicit migration/recovery policy.
39. App Version Compatibility
Every transaction includes app version and schema version.
Backend defines supported client schema versions.
Breaking schema changes require migration or version gating.
Unsupported clients receive a clear update-required response.
Already committed local transactions must remain recoverable after app upgrade.
40. Background Synchronization
Use platform-appropriate background execution where available.
Treat background execution as opportunistic, not guaranteed.
Foreground resume remains the primary recovery trigger.
Do not keep long-lived background sockets solely for sync on mobile platforms.
Respect OS battery/network restrictions.

56. Detailed Example — Timeout After Server Commit
Client sends sale with idempotency key.
Server commits successfully.
Network drops before response arrives.
Client marks transaction READY/retryable, not failed permanently.
Retry sends same key.
Server detects existing idempotency record.
Server returns original result.
Client adopts original invoice ID/version.
No duplicate stock, payment or ledger entry occurs.
57. Detailed Example — Stock Conflict
Device A and Device B have cached stock.
Both attempt offline sales from the same product/batch.
Both create local transactions.
First server submission consumes available stock.
Second submission reaches server and fails the configured stock policy.
Second transaction becomes CONFLICT/REJECTED.
Client preserves the transaction and displays the authoritative stock/result.
Operator may choose an approved adjustment/alternative workflow; no silent negative stock is created.

WebSocket informs connected POS.
Client refreshes authoritative invoice/payment state.
Receipt/payment status updates without duplicate financial posting.

66. Final Synchronization Architecture
The system uses a durable, encrypted, transaction-envelope-based synchronization model. Flutter commits supported offline operations atomically into SQLCipher, then independently uploads immutable envelopes using stable idempotency keys. PostgreSQL validates and commits authoritative financial effects atomically. Incremental server changes are consumed through opaque cursors and applied transactionally. Conflicts are explicit and never resolved through unsafe last-write-wins. Crash recovery treats uncertain network outcomes as retryable with the same identity, ensuring that server-side idempotency converts uncertain delivery into safe exactly-once business effect.
This document is the implementation baseline for Document 06 — Complete Inventory & Batch Engine Specification.
Appendix A — State Transition Rules
READY -> UPLOADING only when eligible.
UPLOADING -> ACCEPTED when server commits.
UPLOADING -> DUPLICATE when server reports an existing idempotent operation.
UPLOADING -> CONFLICT for resolvable business state divergence.
UPLOADING -> REJECTED for non-retryable invalid operations.
UPLOADING -> READY for transient failure.
ACCEPTED/DUPLICATE -> SYNCED after local reconciliation.
CONFLICT -> RESOLVED/BLOCKED only through an explicit resolution workflow.
REJECTED -> RESOLVED/BLOCKED; never silently retried forever.

Appendix B — Developer Rules
Never generate a new idempotency key for a retry.
Never advance a cursor before applying its page.
Never delete a pending transaction to fix a sync problem.
Never overwrite authoritative financial data with cached local state.
Never resolve stock/ledger conflicts by timestamp alone.
Never assume HTTP timeout means failure.
Never assume WebSocket delivery means persistence.
Never expose raw synchronization internals to operators as the primary UI.
Never put credentials or encryption keys in diagnostic output.
