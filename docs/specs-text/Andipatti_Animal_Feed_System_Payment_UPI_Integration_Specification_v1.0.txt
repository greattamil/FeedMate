This document defines the authoritative payment boundary for cash, UPI, bank transfer, Khata and split tender. It covers payment intents, dynamic QR, provider callbacks, status polling, idempotency, refunds, reconciliation, offline restrictions, accounting integration, security, observability and failure recovery.
1. Document Control
2. Purpose, Scope & Objectives
Provide a secure and idempotent payment abstraction independent of a single provider.
Support UPI dynamic QR and provider payment-intent workflows.
Support cash, bank and Khata as payment methods.
Support split tender with exact reconciliation.
Verify asynchronous payment through signed webhook and/or trusted provider status API.
Prevent duplicate payments, duplicate invoice finalization and duplicate refunds.
Separate payment state from printer/WhatsApp/hardware state.
Support delayed payment confirmation and reconciliation.
Provide payment/accounting traceability from intent to settlement.
Support provider outages without corrupting POS financial state.
3. Non-Goals
Do not hardcode a specific payment provider into POS domain logic.
Do not treat QR display as proof of payment.
Do not treat client callback/UI success as proof of payment.
Do not store UPI PIN, bank credentials or other prohibited payment secrets.
Do not use Redis as the financial source of truth.
Do not allow payment provider retries to create duplicate internal payments.
4. Core Payment Principles
Provider integrations are adapters behind a stable PaymentProvider interface.
PostgreSQL is the internal authoritative ledger of payment records and allocation state.
Provider responses are untrusted until signature/authenticity and amount/reference checks pass.
Every payment command has an idempotency identity.
Every webhook has a unique provider event identity where available.
Payment amount must match the expected invoice/intent amount according to explicit tolerance/rounding rules.
Paid state is established only from an authoritative verified provider response or valid internal tender confirmation such as cash.
External network calls never hold an open database transaction unnecessarily.
Financial finalization is atomic; external calls are coordinated through explicit states and outbox/reconciliation.

9. Payment Intent Lifecycle
POS requests payment intent with cart/invoice reference or a controlled pre-finalization payment reference.
Backend validates tenant, amount, currency and idempotency.
PaymentService creates provider-side intent/order/reference.
Provider response is validated and stored.
Backend returns QR/display payload and intent identifiers to Flutter.
Flutter displays dynamic QR/payment UI.
Provider webhook/status callback updates internal state after verification.
PaymentService verifies amount/currency/order/reference.
Payment is marked PAID only when authoritative criteria pass.
POS finalization allocates the verified payment, or a configured post-payment finalization workflow proceeds.
Outbox emits payment status events.
Receipt is generated from final invoice/payment allocation.
10. Pre-Finalization vs Post-Payment Design
The implementation must choose and consistently apply one of two safe orchestration patterns:
For ordinary POS UPI, payment-first with a short-lived cart/payment reference is recommended when the provider supports it, because it avoids creating a finalized invoice before settlement. Regardless of pattern, no payment is allocated twice and no client-only success can finalize a paid invoice.
11. Dynamic UPI QR
QR payload must be generated from the verified payment provider intent.
Amount, merchant identity and transaction reference must originate from trusted backend/provider data.
QR must have an explicit expiration/validity window when supported.
Flutter displays QR but does not alter its financial content.
Reusing an expired intent requires a new intent or provider-supported retry.
Do not generate arbitrary static QR strings in the POS as a substitute for a configured payment workflow unless the tenant explicitly operates a static-QR reconciliation model.
Static QR can be supported as a separate payment mode only if settlement identification and reconciliation are sufficiently reliable; it must not be silently treated as equivalent to dynamic intent-based UPI.
12. Payment Display & Soundbox
Optional customer display may show amount and QR.
Soundbox/voice notification is informational.
Neither QR display nor soundbox output is authoritative.
Provider verification determines internal PAID state.
Soundbox failures never change payment state.
Any hardware event can be correlated to intent ID for diagnostics.
13. WebSocket Payment Updates
WebSocket is an acceleration channel for UI updates.
Only authenticated terminals/users may subscribe to authorized payment events.
Events include intent ID, state, timestamp and safe display fields.
Do not send provider secrets or unnecessary PII.
Events may be lost; Flutter must recover by querying payment status.
Out-of-order events must not cause state regression.
Payment event:
{
  "type": "payment.status",
  "intent_id": "...",
  "state": "PAID",
  "amount": 1250.00,
  "occurred_at": "server-time",
  "version": 7
}

Client rule:
ignore stale event versions and re-query after reconnect.
Exact API schema is governed by Document 02.
14. Polling Fallback
After QR presentation, Flutter receives polling parameters.
Poll at bounded intervals.
Stop on PAID, FAILED, EXPIRED or CANCELLED.
On WebSocket reconnect, refresh current status.
On app restart, recover active intent by ID.
After timeout, leave payment in PENDING/UNKNOWN according to provider contract and provide reconciliation action.
Never create a new payment merely because the UI timed out.
Polling intervals must be configurable and rate-limited to protect provider and backend capacity.
15. Provider Webhook Security
Receive webhook over HTTPS.
Validate provider signature/HMAC/public-key signature according to provider contract.
Validate timestamp/replay protection when provider supplies it.
Validate event ID/idempotency key.
Persist the raw/normalized event metadata required for audit before applying state transition.
Verify merchant/tenant mapping.
Verify provider transaction/reference.
Verify amount and currency.
Apply state transition only if valid.
Return provider-required acknowledgement promptly.
Perform longer reconciliation asynchronously.
Webhook endpoint must be designed for duplicate delivery.
Unknown provider event types are retained and safely acknowledged according to provider guidance, then monitored.
Invalid signatures are rejected and alerted.
16. Never Trust Client Paid Flag
The Flutter client may display a provider SDK result or user-facing success screen, but it cannot directly set a financial payment record to PAID.
Client may request refresh.
Client may report that the customer claims to have paid.
Client may show pending.
Only backend/provider verification changes authoritative state.
Manual payment confirmation, if supported for bank/cash exception workflows, requires explicit permission, evidence and audit and must not be confused with ordinary UPI success.
17. Amount & Currency Validation
Intent amount is stored as NUMERIC(12,2) or stronger configured precision.
Currency is explicit; INR is the expected primary currency for this system.
Provider callback amount must equal expected amount under the provider's exact minor-unit rules.
Any mismatch enters PAYMENT_AMOUNT_MISMATCH/reconciliation review.
Do not round a mismatch away.
Payment allocation cannot exceed invoice due unless explicit overpayment workflow exists.
Expected: INR 1250.00
Provider: INR 1250.00 -> acceptable
Provider: INR 1249.00 -> reject/reconcile
Provider: INR 1250.50 -> reject/reconcile
Provider: wrong currency -> reject/reconcile
18. Reference and Correlation IDs
Persist relationships between all applicable identifiers. Never rely on invoice number alone for provider idempotency.
19. Idempotency Model
Create-intent requests use Idempotency-Key.
Repeated identical create-intent requests return the existing internal intent/result.
Same key with different amount/cart fingerprint returns IDEMPOTENCY_CONFLICT.
Webhook provider_event_id is unique per provider account/event scope.
Payment allocation uses an idempotency identity tied to payment + invoice allocation.
Refund requests use their own idempotency key.
Network timeout after provider creation is resolved through lookup by merchant reference before creating another provider order.
Idempotency records must be retained long enough to cover realistic retry and reconciliation windows, subject to retention policy.
20. Split Tender
Split tender is a controlled composition of multiple tender allocations.
Invoice due = 1,000.00
Cash accepted = 400.00
UPI verified = 600.00
Accepted total = 1,000.00
Residual = 0.00 -> finalize

Invoice due = 1,000.00
Cash = 400.00
UPI = 599.99
Residual = 0.01 -> do not silently finalize unless explicit rounding policy permits it.
Cash received may exceed cash allocation because change is separately calculated.
UPI intent should normally be created for the exact remaining amount.
Khata can be used for a remaining amount only if customer credit policy allows it.
Every component must reach an accepted terminal/authorized state before paid finalization.
21. Cash Tender
Cashier enters amount received.
System computes change = received − allocated cash amount.
Change cannot be negative unless the UI interprets input as exact tender rather than received amount.
Cash movement is recorded in the active cash session.
Physical cash count is reconciled at EOD.
Cash tender is not dependent on provider webhooks.
22. Bank Transfer
Bank transfer payment method is configurable.
Capture bank/reference number where appropriate.
Verification policy can be manual, provider-backed or reconciliation-based.
Manual confirmation requires permission, evidence/reason and audit.
Unverified bank claim must remain pending/unverified.
Bank settlement reconciliation must not create duplicate internal payment records.
23. Khata Tender
CreditService/KhataService validates customer credit exposure.
Credit limit, overdue and grace rules come from Document 07.
Owner/admin override is explicitly audited.
Khata is an internal receivable, not an external payment-provider settlement.
Invoice + receivable + stock + accounting are atomic.
24. Payment Allocation
Identify invoice/receivable target.
Verify payment is PAID/authorized tender.
Verify unallocated payment amount.
Lock payment allocation state.
Validate remaining invoice due.
Create allocation.
Update allocation totals atomically.
Post/complete accounting mapping.
Commit and emit event.
A single payment can be allocated to one or multiple invoices only when the accounting model explicitly supports it.
Allocation cannot exceed available verified payment amount.
Reallocation requires controlled reversal/new allocation, not direct mutation of historical allocation.
25. Payment + Invoice Finalization
When payment-first is used, the recommended sequence is:
Calculate final cart quote.
Create payment intent for exact expected amount.
Verify payment PAID.
Begin short database transaction.
Revalidate cart, price/tax snapshot, customer and inventory.
Lock/select document series.
Allocate stock.
Create invoice.
Create invoice tax lines.
Allocate verified payment.
Post accounting/Khata/cash as applicable.
Create audit and outbox entries.
Commit.
Trigger receipt/notification after commit.
If payment becomes invalid or stock becomes unavailable before finalization, the invoice must not finalize. The verified payment remains separately traceable and is reconciled/refunded according to provider workflow; never create a replacement payment silently.

27. Payment Pending UX
Show amount, customer instruction, QR and countdown where applicable.
Show PENDING state clearly.
Provide Refresh/Check Status.

28. Offline Payment Policy
Cash can be supported offline according to POS cash policy.
Khata can be supported offline only under explicit offline credit policy and later server validation.
UPI must not be considered verified offline solely from a client/QR display.
Static UPI QR workflows may be recorded as UNVERIFIED and reconciled later only if explicitly configured.
Bank transfer claims remain pending unless an offline trusted process exists.
Offline payment records use transaction envelopes and stable client IDs.
Reconnection performs idempotent upload and reconciliation.

30. Refunds
30.1 Refund principles
Refunds are linked to original payment and invoice/return where applicable.
Refund amount cannot exceed refundable remaining amount.
Provider refund operation is idempotent.
Refund state is independent from original payment PAID state.
Partial refunds are supported if provider and business policy allow.
Refund completion requires provider verification or authorized internal settlement method.
30.2 Refund states
31. Refund Workflow
Validate original invoice/payment and return/credit-note eligibility.
Calculate refundable amount.
Check prior refunds.
Create refund with idempotency key.
Submit provider refund.
Persist provider refund reference.
Receive webhook/status.
Verify amount/reference.
Mark refund state.
Post accounting/receivable reversal when refund is confirmed.
Notify customer asynchronously.
32. Chargeback/Dispute Extension
Provider dispute events should be accepted through a future dispute adapter.
Do not automatically reverse invoices without documented business/accounting workflow.
Store dispute evidence/reference.
Expose reconciliation task to finance/admin.
Maintain original payment and invoice audit chain.
33. Reconciliation Engine
Reconciliation detects differences between internal records and provider/bank settlement.
Fetch provider settlement/status data.
Normalize provider records.
Match by provider transaction/reference.
Compare amount/currency/state.
Create reconciliation result.
Auto-resolve safe idempotent differences.
Create exception for unresolved mismatch.
Audit and notify finance.

35. Payment Webhook Event Processing

44. Webhook Idempotency & Ordering
Store provider_event_id before or atomically with state application.
If an event is already processed, return success without repeating side effects.
Use payment version/state transition sequence where provider supplies ordering.
Do not regress PAID to PENDING because of a late callback.
Do not regress REFUNDED to PAID.
Out-of-order events are logged and reconciled.
45. Timeouts & Unknown Outcomes
A timeout is not a payment failure. The provider may have accepted the transaction before the network timed out.
Mark API attempt as UNKNOWN/REQUIRES_STATUS_CHECK.
Lookup by merchant reference/provider order ID.
If provider says PAID, update internal state idempotently.
If provider says FAILED/EXPIRED, update accordingly.
If provider cannot determine, keep pending/unknown and schedule reconciliation.
Never blindly create a second intent.
46. Provider Outage
Detect elevated provider failures via metrics/health checks.
Do not falsely mark payments failed solely from local timeout if provider outcome is unknown.
Allow alternate tender methods if the cashier chooses and policy permits.
Prevent duplicate charging when retrying.
Provide finance/admin reconciliation for transactions created near outage window.
47. Duplicate Customer Payment
If a customer pays twice, the system must preserve both provider transactions rather than collapsing them.
First verified payment may settle the invoice.
Second verified payment becomes an unallocated/excess payment exception or explicit customer credit/refund workflow.
Do not silently allocate both to the same invoice.
Finance can refund or allocate excess according to policy.
Both transactions remain traceable.
48. Overpayment
Reject over-allocation by default.
If tenant supports customer wallet/advance, excess can be posted to a dedicated liability/advance account.
If tenant does not support advances, create refund/reconciliation workflow.
Never discard excess money.
Audit the resolution.
49. Payment Expiry
Expired intent cannot be treated as paid.
Flutter disables stale QR where practical.
New intent uses a new idempotency/payment-attempt identity.
Old intent remains in history.
Late provider success is handled by reconciliation rather than silently creating a duplicate invoice.

68. Non-Negotiable Payment Rules
Never trust a client-only paid flag.
Never treat a QR scan/display as proof of payment.
Never create a second provider intent merely because a prior request timed out.
Never allocate a payment above its verified unallocated amount.
Never accept a provider callback without required authenticity verification.
Never ignore amount or currency mismatch.
Never process the same provider event twice.
Never allow payment state to regress because of an old/out-of-order event.
Never finalize a paid invoice without verified/authorized tender according to policy.
Never edit historical payment records to hide discrepancies; use compensating/reconciliation records.
Never let printer, WhatsApp or soundbox state determine payment state.
Never store provider secrets in the Flutter app.
Never bypass tenant isolation or RLS.
Never silently discard overpayments or duplicate customer payments.
Never delete payment traceability when archiving invoices.

Conflict | Resolution
Same idempotency key, same payload | Return original result.
Same key, different payload | IDEMPOTENCY_CONFLICT.
Client says PAID, provider says PENDING | Provider/verified backend state wins; keep pending.
Client says PAID, provider says FAILED | Do not allocate; reconcile exception.
Two provider transactions for one invoice | Preserve both; settle first and route excess.
Payment allocated twice | Prevent with allocation lock/idempotency; reconcile if detected.
Refund success externally, internal pending | Reconciliation updates internal state.
Unknown provider transaction | Manual/automated reconciliation required.
