Andipatti Animal Feed System
Document 18 — Complete Seed Data, Master Configuration & Initial Setup Specification v1.0
Implementation-ready specification for provisioning a new tenant/shop, establishing authoritative master data, configuring products, UOMs, tax, pricing, suppliers, customers, roles, devices, document series, accounting controls, hardware and operational defaults. No sprint planning.
1. Purpose, Scope, Objectives & Non-Goals
1.1 Purpose
Define a deterministic, auditable and safe first-time setup process so a new animal-feed shop can begin operations without unsafe hardcoded assumptions or incomplete master data.
1.2 Scope
Tenant/shop creation and onboarding
Users, roles and permissions
Financial year and document series
Products, categories, brands, barcodes and aliases
UOMs and product-specific conversions
Tax profiles and HSN/GST configuration
Customer tiers, price lists and credit policy
Customers, suppliers and opening balances
Locations, bins and stock configuration
Payment providers and tender configuration
Hardware/device registration
Notification/WhatsApp templates
Inventory opening stock and batches
Accounting/chart-of-accounts defaults
Retention, backup and operational settings
Seed execution, validation, import, rollback and audit
1.3 Non-Goals
Legal advice or permanently hardcoded tax rates/thresholds
Production secrets embedded in seed files
Automatic invention of real supplier/customer records
Sprint planning
2. Master Data Principles
Reference/master data is controlled and versioned.
Transactional records snapshot relevant master values at finalization.
Effective dating is mandatory for pricing and tax configurations that can change.
Seed data must be idempotent and safe to rerun.
Tenant-owned records carry tenant_id and are protected by PostgreSQL RLS.
Global reference data must never leak tenant-specific commercial data.
Every sensitive setup change is audited.
Unknown values remain configurable rather than being guessed.

83. End-to-End Setup Scenarios
83.1 Fresh Shop
Provision tenant → owner → roles → FY → series → locations → products/UOM/tax → pricing → payment → hardware → backup → readiness validation → production.
83.2 Existing Shop Migration
Backup source → map masters → import/validate → opening stock/balances → reconcile → cutover → monitor.
83.3 Product Price Change
Create future/effective price → authorize → activate → preserve historical invoice snapshots.
83.4 Tax Change
Create approved effective-dated tax profile → validate → activate at effective time → preserve historical tax snapshots.
83.5 Device Replacement
Revoke old device → register replacement → download authorized configuration → sync → hardware test → audit.
83.6 Disaster Rebuild
Restore authoritative database/configuration → do not reseed transactions → restore Docker infrastructure → validate masters/RLS → reconcile → resume.
83.7 Seed Rerun
Execute same seed version twice → no duplicate records → stable identifiers/checksums → audit only records actual changes.
83.8 Opening Stock Error
Detect discrepancy → freeze affected posting → investigate source evidence → controlled adjustment/reversal → audit; do not delete history.

85. Mapping to Previous Documents
86. Final Architecture Summary
Document 18 establishes a controlled configuration foundation: reference data is versioned, tenant data is isolated, financial and tax settings are effective-dated, products and UOMs are explicit, pricing is configurable, opening balances are evidence-backed, hardware and providers are securely provisioned, and production readiness requires validation plus verified backup. The seed system is designed to be rerunnable without duplication and safe for fresh, test, migration and recovery environments.
87. Important Production Note
Business defaults such as 2% farmer discount, 5% wholesale discount, example collection dates, tare thresholds, tax classifications and product categories are configuration examples. Before production, the shop owner/operator must approve actual values and current tax/compliance requirements must be verified. The application must keep such values configurable and effective-dated rather than embedding them as immutable code constants.
