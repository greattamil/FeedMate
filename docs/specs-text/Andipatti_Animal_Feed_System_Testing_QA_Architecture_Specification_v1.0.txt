Document 14 — Complete Testing & QA Architecture / Specification v1.0
Implementation-ready quality engineering, test architecture, automation, environments, test data, security testing, financial/inventory integrity testing, hardware testing, offline testing, performance, release qualification and production verification. No sprint planning.
1. Purpose, Scope, Objectives & Non-Goals
1.1 Purpose
Define the quality strategy and executable acceptance model for the Flutter application, Go backend, PostgreSQL, offline SQLCipher database, Docker platform, integrations, hardware and business workflows.
1.2 Scope
Functional, integration, system, regression and end-to-end testing.
Unit and domain tests for pricing, tax, inventory, accounting, Khata, payment and compliance logic.
API, database, RLS, authorization and security testing.
Flutter widget, golden, accessibility, device and offline/synchronization testing.
Barcode, scale, ESC/POS printer, cash drawer and payment-display testing.
Payment/UPI webhook, reconciliation and refund testing.
GST/e-invoice/e-way and export testing using approved sandbox/test environments.
Docker/container, migration, backup/restore and deployment verification.
Performance, load, concurrency, resilience, chaos and recovery testing.
Release gates, defect management, production smoke tests and evidence retention.
1.3 Quality Objectives
Prevent incorrect financial, tax and inventory outcomes.
Prove tenant isolation and authorization boundaries.
Prove offline operation without compromising server authority.
Detect integration and hardware failures without corrupting transactions.
Make every production release repeatable, observable and rollback-safe.
Provide automated regression coverage for critical business invariants.
1.4 Non-Goals
This document does not replace independent penetration testing or legal/compliance certification.
Exact government/provider test cases must follow the current provider sandbox and authoritative specifications.
No sprint planning is included.
2. Quality Principles
Test business invariants, not only UI behavior.
Prefer deterministic automated tests for critical logic.
Use realistic decimal precision and never floating-point assumptions for money.
Every financial/inventory mutation must be tested for idempotency and concurrency.
Tenant isolation is tested at both Go authorization and PostgreSQL RLS layers.
External providers are mocked/simulated for deterministic tests and separately validated in sandbox environments.
Hardware is tested through simulators plus physical-device certification.
Offline tests include disconnects, retries, crashes, replay and revoked-device scenarios.
Production smoke tests must be safe and non-destructive.
A release is qualified by evidence, not by test count alone.

9. PostgreSQL RLS Security Testing
RLS testing is mandatory for every tenant-owned table.
Create at least two isolated tenants.
Create representative records in each tenant.
Authenticate as a user from tenant A and verify tenant A access.
Attempt direct and indirect reads of tenant B records; verify rejection/empty result as designed.
Attempt inserts with a forged tenant_id; verify server/RLS behavior.
Attempt updates/deletes against tenant B IDs; verify rejection.
Test joins that could accidentally bypass tenant boundaries.
Test worker/job connections with explicit tenant context.
Test support/admin roles separately and verify only intended cross-tenant access.
Run the suite after every schema/security policy change.

44. Test Data Privacy
Synthetic data is the default.
Mask customer phone/name/address and tax identifiers before lower-environment use.
Never put production payment credentials in tests.
Do not include real secrets in fixtures.
Clean temporary exports and uploaded test files after test completion.
Control access to test reports containing sensitive data.
45. Test Failure Recovery
A failed test must identify the affected environment and artifact.
Do not automatically suppress flaky failures.
Quarantine flaky tests with an owner and expiry date.
Retry only when the test framework can distinguish infrastructure flakiness from product failure.
Critical business-invariant tests are never ignored to unblock a release.
46. Test Coverage Targets
Coverage percentage alone is not a release criterion; critical path and invariant coverage take precedence.

52. Non-Negotiable QA Rules
Never release with known financial, inventory or tenant-isolation corruption.
Never bypass RLS tests.
Never accept client-side payment status as authoritative in tests or production.
Never ignore idempotency failures on financial endpoints.
Never use last-write-wins to hide financial/inventory conflicts.
Never use real production secrets in test environments.
Never copy unmasked production PII into lower environments.
Never suppress flaky critical tests without controlled quarantine and review.
Never consider UI-only success sufficient for a transaction; verify DB/accounting/inventory state.
Never call a deployment successful without health, smoke and observability verification.

54. Final QA Architecture Summary
Quality is enforced as a layered system: deterministic domain tests protect business mathematics; PostgreSQL integration and RLS tests protect authoritative data; API/authorization tests protect boundaries; Flutter tests protect the operator experience; offline tests protect synchronization integrity; hardware tests isolate physical failures; payment/compliance tests protect external state transitions; security and container tests protect the platform; performance/reliability tests protect operations; and end-to-end reconciliation proves that invoice, inventory, accounting, payment and reporting outcomes agree.
