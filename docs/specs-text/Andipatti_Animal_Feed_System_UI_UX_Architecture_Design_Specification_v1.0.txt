Andipatti Animal Feed System
Document 15 — Complete UI/UX Architecture & Design Specification v1.0
Implementation-ready Flutter UI/UX specification for a fast, Tamil-friendly, offline-first animal-feed retail/wholesale POS and operations application. Covers operator workflows, information architecture, screens, components, states, accessibility, hardware interaction, responsive behavior, localization, security UX and acceptance criteria. No sprint planning.
1. Purpose, Scope, Objectives & Non-Goals
1.1 Purpose
Define the complete user experience and interface contract so Flutter implementation remains consistent across POS, procurement, inventory, customers/Khata, payments, GST/compliance, reporting, hardware, synchronization and administration.
1.2 Objectives
Optimize counter billing for speed, clarity and minimum operator taps.
Support Tamil Unicode, transliteration, phonetic and colloquial product search.
Make offline/online state visible without alarming operators unnecessarily.
Present financial, inventory and payment states unambiguously.
Support touch, barcode, weighing scale and thermal-printer workflows.
Provide role-appropriate navigation and prevent accidental privileged actions.
Remain usable on common Android POS/tablet/phone form factors.
Provide accessible, localized and resilient error/recovery experiences.
1.3 Non-Goals
This document does not define Flutter source code line-by-line; it defines the UI/UX contract.
Visual branding colors, final logo assets and exact typography may be supplied by the product brand guide.
Server-side business rules remain authoritative as specified in Documents 01–14.
2. UX Principles
Counter-first: common sale actions are reachable with minimal navigation.
Tamil-first capability: users may search and operate in Tamil or English.
One clear primary action per screen.
Never hide financial state behind decorative UI.
Prevent errors before submission; explain errors after rejection.
Use progressive disclosure for advanced configuration.
Offline status is persistent and understandable.
Never imply payment success without authoritative confirmation.
Never imply stock availability without current/approved stock state.
Hardware failures degrade gracefully without corrupting transactions.
Destructive actions require clear confirmation and authorization.
Every privileged action shows who approved it when applicable.

46. Security UX
Sensitive screens can require re-authentication based on policy.
Mask secrets and sensitive customer information where appropriate.
Owner PIN entry should obscure digits.
Show session/device security status to authorized administrators.

Do not expose backend stack traces or database details.
Clipboard/screenshot protections may be applied to selected sensitive screens.
47. Privacy UX
Collect only necessary customer/supplier data.
Explain why optional data is requested where appropriate.
Mask phone numbers in lists where full display is unnecessary.
Export/share actions require permission.
Receipt sharing must target the selected customer/transaction only.
Do not display unrelated customer data on public/customer-facing screens.
48. Customer-Facing Display
Show current item, quantity/weight, price and running total.
Show discount/tax where configured for customer clarity.
Show payment QR only for the active payment intent.
Do not display internal cost, margin, supplier data or privileged notes.

49. Printer UX
Show printer connected/disconnected state.
Provide Test Print for authorized users.
After finalization, printing is an output operation.

Tamil receipt preview should match expected thermal rendering as closely as practical.
50. Scale UX
Display connection status and protocol profile.
Show stable reading state.
Tare action is explicit and permission-controlled where appropriate.
Manual fallback is visibly labeled.
Error states explain whether operator should retry, reconnect or use authorized manual entry.
51. Performance UX
POS search should feel immediate using local indexes/cache where permitted.
Show progress for operations that cannot complete instantly.
Avoid blocking the whole screen for background sync.
Use pagination for large histories.
Cache read-only master data according to freshness policy.
Preserve scroll position and form state when safe.
52. Loading & Offline Skeletons
Use skeletons for data-heavy screens.
Use explicit progress for long-running exports.
Do not show infinite spinners without timeout/recovery.
When offline, switch to local data state rather than repeatedly retrying visible reads.
Show stale-data indicators when freshness matters.
53. Navigation & State Preservation
Back navigation must preserve active POS draft unless explicitly abandoned.
Switching tabs must not silently lose entered form data.
Deep links open only allowed screens and must revalidate authorization.
After login/session renewal, return the user to the safe prior context when possible.
After device revocation, sensitive screens are cleared.
54. App Lifecycle & Crash Recovery
Persist safe draft POS state.
Recover incomplete local transactions after crash.
Never resume a privileged screen with stale authorization without revalidation.
If local DB/key cannot be opened, provide a controlled recovery path.
Do not expose crash logs containing PII/secrets.

Never allow the UI to bypass server authorization.
Never silently discard an active POS transaction.

71. Final UX Architecture Summary
The application should feel like a purpose-built retail POS rather than a generic enterprise system: the cashier reaches search, scan, weigh, price, pay and receipt in one focused flow; managers and back-office users receive deeper operational screens; Tamil is a first-class search and display language; offline state is visible but unobtrusive; payment, inventory and financial states are explicit; hardware is integrated without becoming authoritative; and every privileged or irreversible action is deliberate, authorized and auditable.
